## 공통 원칙

1. **발견된 문제의 관련 영역도 재검토** — 문제 수정 후 영향받을 수 있는 코드를 추적하여 추가 검토
2. **모든 spec 파일을 매 이터레이션마다 함께 처리** — 체크리스트 라인 참조로 해당 줄만 Read
3. **이전 이터레이션 이어받기** — 체크리스트/결과 파일로 진행 상황 추적
4. **수정 발생 시 promise 출력 금지** — 수정 없는 클린 이터레이션에서만 promise 출력
5. **검증 이터레이션 필수** — 첫 이터레이션에서는 promise를 출력하지 않는다. 최소 1회 전체 재검증을 통과해야 한다.

## 절차

### 1단계: YAGNI 검토

Task(subagent_type='yagni-reviewer')를 호출한다:
- spec에 명시되지 않은 기능 식별
- 미래 확장을 위한 사전 추상화 식별
- 과도한 설계 패턴 식별
- 범위 초과 테스트 계획 식별
- **DDD 레이어 필요성 검증**: spec의 복잡도 대비 과도한 DDD 세레모니가 계획에 포함되었는지
  - 단순 CRUD에 불필요한 Domain Service/Domain Event가 계획되었는지
  - 하나의 Entity만 있는데 Aggregate Root 패턴이 적용되었는지
  - 외부 연동이 없는데 Anti-Corruption Layer가 계획되었는지
  - Kent Beck Rule 4 (Fewest Elements): 동일한 효과를 더 적은 요소로 달성할 수 있는지

### 2단계: 과설계 제거

yagni-reviewer가 보고한 YAGNI/OVER 항목을 {{PLAN_PATH}}에서 제거한다:
- YAGNI 항목: 해당 Unit에서 완전 제거
- OVER 항목: 간소화 방안에 따라 계획 수정
- GRAY 항목: spec을 재확인하여 필요 여부 판단

### 3단계: 계획 정합성 확인

제거/간소화 후 계획이 여전히 완전한지 확인한다:
- 모든 REQ 항목이 최소 하나의 Unit에 포함되는지
- 제거로 인해 의존 관계가 깨지지 않았는지

수정 사항을 {{NOTES_PATH}}에 기록한다.

**수정이 있었으면 promise를 출력하지 않는다.**

## 완료 조건

- yagni-reviewer YAGNI 항목 0건
- OVER 항목 모두 간소화됨
- DDD 레이어 과잉 적용 0건 (spec 복잡도에 맞는 적정 수준)
- 계획이 여전히 모든 REQ를 커버
- 의존 관계 정합성 유지

- **검증 이터레이션 ≥ 1** (첫 이터레이션 이후 최소 1회 전체 재검증 통과)

모든 조건 충족 시 <promise>YAGNI DONE</promise> 출력.
