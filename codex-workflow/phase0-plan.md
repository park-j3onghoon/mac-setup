## 이어받기 (이전 이터레이션이 있는 경우)

**먼저 {{CHECKLIST_PATH}}가 이미 존재하는지 확인한다.**
- 존재하지 않으면: 1단계부터 새로 시작한다.
- 존재하면: 이전 이터레이션의 작업을 이어받는다. 섹션 처리 현황을 확인하고:
  - `[ ]` 섹션이 있으면 → 2단계(추출) 계속
  - 모든 섹션이 `[E]`이면 → 3단계(검증) 시작
  - 모든 섹션이 `[V]`이고 **Digest가 없으면** → 4단계(Spec Digest 생성)
  - 모든 섹션이 `[V]`이고 **기존 구현 매핑이 없으면** → 5단계(기존 구현 검색)
  - 모든 섹션이 `[V]`이고 **계획이 없으면** → 6단계(계획 수립)
  - 모든 섹션이 `[V]`이고 **계획이 있으면** → 7단계(전수 교차 검증)

## 절차

### 1단계: Spec 섹션 맵 생성

각 spec 파일의 마크다운 헤더를 **Grep으로** 추출한다 (파일 전체를 Read하지 않는다):

```
Grep(pattern="^#{1,4} ", path="spec.md", output_mode="content")
```

Grep 결과에서 각 헤더의 라인 번호를 파악하고, 인접 헤더 간의 라인 범위를 계산하여 섹션 맵을 만든다.

### 2단계: 추출 패스 — 섹션별 요구사항 추출

{{CHECKLIST_PATH}}에 체크리스트를 생성한다. **맨 위에 섹션 처리 현황**을 포함한다:

```markdown
# Spec Checklist

## 섹션 처리 현황
- [ ] spec.md: # Overview (L1-L45)
- [ ] spec.md: ## Domain Entities (L46-L120)
- [ ] spec.md: ## Approval Flow (L121-L200)
...

## 교차 검증 진행
- 마지막 검증 섹션: (없음)
- 완료 라운드: 0

## Domain
(REQ 항목들)

## Application
(REQ 항목들)
...
```

**섹션 상태**:
- `[ ]` — 미처리
- `[E]` — 추출 완료 (Extracted). 1회 읽고 REQ 추출함
- `[V]` — 검증 완료 (Verified). 2회차에 다시 읽고 누락 없음 확인함

**추출 처리 방법**:
1. `[ ]` 상태의 섹션을 하나씩 순서대로 처리한다.
2. 해당 섹션만 Read(offset, limit)로 읽는다.
3. 읽은 내용에서 요구사항을 추출하여 체크리스트에 REQ 항목으로 추가한다.
4. 해당 섹션을 `[E]`로 변경한다.
5. 다음 `[ ]` 섹션으로 넘어간다.

**컨텍스트 관리**: 한 이터레이션에서 모든 섹션을 처리할 필요 없다. 처리한 데까지 저장하고 다음 이터레이션에서 이어받는다.

**체크리스트 작성 규칙**:
1. 요약하지 않는다. 해당 라인 범위의 핵심 동작/조건을 한 줄로 정확히 기술한다.
2. 하나의 요구사항에 여러 조건이 있으면 **조건마다 별도 REQ 항목**으로 분리한다.
3. 라인 참조 `[파일명:시작줄-끝줄]`은 반드시 정확해야 한다. 나중에 이 참조로 원본을 읽는다.
4. 암묵적 요구사항(명시되지 않았지만 문맥상 필요한 것)도 추출하되, `(암묵적)` 표시를 붙인다.
5. **부정 요구사항**("~하지 않는다", "~를 금지한다", "~이면 안 된다", "~해서는 안 된다", "~불가", "~제외" 등)을 명시적으로 추출한다. `(부정)` 표시를 붙인다.
6. **정량적 요구사항**(성능 임계값, 크기 제한, 타임아웃, 페이지 크기, 재시도 횟수, 비율, 개수 제한 등)을 **정확한 숫자와 함께** 추출한다. `(정량)` 표시를 붙인다. 예: "페이지당 20건 (정량)", "타임아웃 5초 (정량)".
7. **참조 요구사항**("기존 X와 동일하게", "Y처럼 동작", "Z 방식을 따른다" 등)을 추출하고 참조 대상을 명시한다. `(참조)` 표시를 붙인다. 예: "기존 주문 승인 프로세스와 동일한 상태 전이 (참조: orders/services.py:approve)".
8. DDD 레이어별로 그룹핑한다: Domain → Application → Adapter → Test → 기타.

### 3단계: 검증 패스 — 누락 확인 (모든 섹션이 `[E]`가 된 후)

**모든 섹션이 `[E]`가 되면 검증 패스를 시작한다.**

`[E]` 상태의 섹션을 하나씩:
1. 해당 섹션을 Read(offset, limit)로 **다시** 읽는다.
2. 해당 라인 범위를 참조하는 기존 REQ 항목들을 체크리스트에서 찾는다.
3. 원본 spec 내용과 REQ 항목들을 **한 줄씩** 대조한다:
   - 빠뜨린 요구사항이 없는지
   - 하나의 REQ에 2개 이상의 독립된 조건이 뭉쳐있지 않은지
   - 라인 참조가 정확한지
4. 누락된 요구사항이 있으면 REQ 항목을 추가한다.
5. 해당 섹션을 `[V]`로 변경한다.

**한 이터레이션에서 모든 `[E]` 섹션을 검증할 필요 없다.** 처리한 데까지 저장하고 다음 이터레이션에서 이어받는다.

### 4단계: Spec Digest 생성 (모든 섹션이 `[V]`가 된 후)

체크리스트의 REQ 항목과 원본 spec을 종합하여 **Spec Digest** (스펙 요약 인덱스)를 {{DIGEST_PATH}}에 생성한다.
Spec Digest는 대형 spec(수천 줄)에서 교차 참조 누락을 방지하기 위한 "큰 그림" 파일이다.
**모든 후속 Phase가 작업 시작 전에 이 파일을 먼저 읽는다.**

**Digest 작성 규칙:**

```markdown
# Spec Digest

## 핵심 도메인 개념
- [개념명]: [정의 위치] 정의, [제약 위치] 제약사항 요약
  (예: 할인율: [spec.md:45] 정의, [spec.md:520] 상한 30%, [spec.md:780] VIP 예외)

## 교차 참조 맵
- 섹션 X ↔ 섹션 Y: [관계 설명]
  (예: 섹션 A(주문) ↔ 섹션 F(할인): 주문 금액에 등급별 할인율 적용)

## 전역 제약사항
- 모든 (정량) REQ를 한곳에 모은다 (숫자와 위치)
- 모든 (부정) REQ를 한곳에 모은다
- 모든 (참조) REQ를 한곳에 모은다 (참조 대상 명시)

## 엔티티 관계
- [Entity A] → [Entity B]: [관계 설명]
  (예: Order → OrderItem: 1:N, Order → Member: N:1)
```

**작성 절차:**
1. 체크리스트의 모든 REQ 항목을 읽는다.
2. REQ에서 등장하는 **도메인 개념**(Entity, VO, 비즈니스 규칙)을 추출한다.
3. 같은 개념이 **여러 섹션에 걸쳐** 언급되는 경우 교차 참조 맵에 기록한다.
4. `(정량)`, `(부정)`, `(참조)` 태그가 붙은 REQ를 전역 제약사항에 모은다.
5. Entity 간 관계를 정리한다.

**크기 제한**: Digest는 **200줄 이내**로 유지한다. 요약이므로 상세 내용은 체크리스트의 라인 참조를 통해 원본 spec에서 읽는다.

### 5단계: 기존 구현 검색 (Digest 생성 후)

**계획을 수립하기 전에, 기존 코드베이스에서 이미 구현된 기능을 검색한다.**
Shotgun surgery를 방지하려면 새로 만들지 말고 기존 코드를 호출해야 한다.

**검색 방법**:
1. 체크리스트의 REQ 항목에서 핵심 동작/개념 키워드를 추출한다.
2. {{MODULE_PATH}}와 프로젝트 전체에서 Grep/Glob으로 검색한다:
   - 동일/유사 함수명 (예: REQ가 "할인율 계산"이면 → `discount`, `할인`, `calculate_rate` 등 검색)
   - 동일 도메인 개념의 Entity/VO/Service (예: REQ가 "승인 상태 전이"면 → `Approval`, `approve`, `status` 검색)
   - 동일 패턴의 Repository 메서드 (예: `get_by_`, `filter_by_`, `bulk_` 등)
   - 동일 기능의 유틸리티 함수 (날짜 계산, 금액 변환, 검증 로직 등)
3. 발견된 기존 코드를 Read로 읽고, REQ의 요구사항과 **기능이 일치하는지** 확인한다.

**결과를 체크리스트에 기록한다**:
```markdown
## 기존 구현 매핑
- REQ-003 → 기존: utils/pricing.py:calculate_discount() — 그대로 호출 가능
- REQ-007 → 기존: common/validators.py:validate_date_range() — 시그니처 다르나 래핑하여 재사용 가능
- REQ-012 → 기존 없음 — 신규 구현 필요
```

**판정 기준**:
- **그대로 호출**: 기존 함수/메서드가 REQ를 완전히 충족 → 새로 만들지 않고 호출
- **래핑하여 재사용**: 기존 코드가 부분적으로 충족 → 어댑터/래퍼로 재사용
- **신규 구현**: 기존에 해당 기능 없음 → 새로 작성

### 6단계: 구현 계획 수립

체크리스트의 REQ 항목들을 구현 Unit으로 묶어 {{PLAN_PATH}}에 저장한다.
**5단계에서 "그대로 호출" 또는 "래핑하여 재사용"으로 판정된 REQ는 별도 표시한다.**

```markdown
# 구현 계획

## 기존 코드 재사용
- REQ-003: utils/pricing.py:calculate_discount() 호출
- REQ-007: common/validators.py:validate_date_range() 래핑

## Unit 1: Domain entities
- REQ-001, REQ-002 (신규)
- 구현 파일: domain/entities.py, domain/value_objects.py
- 의존: 없음

## Unit 2: Domain services
- REQ-005, REQ-006 (신규)
- 구현 파일: domain/services.py
- 의존: Unit 1
...
```

**Unit 구성 규칙**:
- DDD 레이어 순: domain → application → adapter
- 각 Unit은 **하나의 이터레이션**에서 구현 가능한 크기 (REQ 5~10개 이내)
- Unit 간 의존 관계를 명시한다
- **기존 코드 재사용 REQ는 Unit에 포함하지 않는다** (호출만 하므로 별도 구현 불필요)

### 7단계: 전수 교차 검증 (계획 수립 후, 매 이터레이션 반복)

**계획이 수립된 후에도 promise를 바로 출력하지 않는다.**
남은 이터레이션을 활용하여 체크리스트와 원본 spec을 교차 검증한다.

**절차:**
1. {{CHECKLIST_PATH}}의 "교차 검증 진행"에서 **마지막 검증 섹션**을 확인한다.
2. 그 다음 섹션부터 순서대로 Read(offset, limit)로 읽는다.
3. 해당 섹션의 spec 원문과 체크리스트 REQ 항목을 **한 줄씩** 대조한다:
   - 체크리스트에 없는 요구사항 → REQ 추가 + 계획 업데이트
   - REQ의 기술이 부정확 → REQ 수정
   - 라인 참조 오류 → 수정
4. 확인한 섹션까지 "마지막 검증 섹션"을 업데이트한다.
5. 모든 섹션을 한 바퀴 돌면 "완료 라운드"를 +1한다.

**한 이터레이션에서 모든 섹션을 교차 검증할 필요 없다.** 처리한 데까지 저장하고 다음 이터레이션에서 이어받는다.

**누락 발견 시**: REQ를 추가하고 계획을 업데이트한다. promise를 출력하지 않는다.

**누락 미발견 시**: 아래 두 조건을 **모두** 충족해야 promise를 출력할 수 있다.
1. 완료 라운드가 2 이상
2. **이번 이터레이션에서 직접 최소 1개 섹션을 Read하고 대조를 수행했을 것** — 이전 세션의 카운터만 확인하고 promise를 출력하는 것은 금지. 반드시 이번 이터레이션에서 spec 원문을 직접 읽고 대조한 결과 누락 0건이어야 한다.

## 완료 조건

- 섹션 처리 현황의 **모든 섹션**이 `[V]` (추출+검증 완료)
- **교차 검증 완료 라운드 ≥ 2** (계획 수립 후 전체 섹션을 최소 2바퀴 재검증)
- **기존 구현 매핑 완료**: 모든 REQ에 대해 기존 코드 검색을 수행하고 결과를 기록
- 체크리스트의 모든 REQ 항목이 계획의 Unit 또는 "기존 코드 재사용" 섹션에 포함됨
- {{CHECKLIST_PATH}}에 체크리스트 파일 저장 완료
- {{DIGEST_PATH}}에 Spec Digest 파일 저장 완료 (200줄 이내)
- {{PLAN_PATH}}에 계획 파일 저장 완료
- 계획이 CLAUDE.md 아키텍처 원칙과 정합

모든 조건 충족 시 <promise>PLAN DONE</promise> 출력.
