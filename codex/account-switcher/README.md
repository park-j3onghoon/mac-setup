# Codex 사용량에 따른 계정 자동 전환

`codex`로 시작하는 대화형 세션은 회사 계정을 우선 사용한다. 회사가 90% 이상이고
개인이 90% 미만이면 개인으로 전환한다. 둘 다 90% 이상이면 자동 전환은 현재 계정을 유지한다.
비대화형 `exec`의 시작 계정 선택은 이 경우 회사 계정을 사용한다.
각 서비스의 실제 사용 한도는 그대로 적용되며 이 실행기가 한도를 늘리지는 않는다.

자동 서버의 우선 계정은 `~/.codex-auto/account-switcher.json`의 `preferred`로
저장한다(기본 `company`, 개인 우선은 `personal`). 개인 우선이면 개인이 90% 이상일
때 회사로 전환하고, 개인 사용량이 다시 90% 미만이면 개인으로 돌아온다.
이 설정은 공유 자동 서버에 적용되며 비대화형 `exec`의 시작 계정 선택은 회사 우선이다.
대시보드에서 ID를 고르면 `~/.codex-auto/preference.json`의 `preferred`와 `requested_at`을
감독이 읽고 사용량을 다시 확인한다. `immediate: true`인 수동 선택은 기존 90% 규칙으로
선택한 계정을 쓸 수 있을 때 유휴 대기 없이 로그인한다. 실행 중인 턴은 이때 실패할 수 있다.
자동 전환은 계속 유휴 상태를 기다린다. 처리 결과는 `account-switcher.json`의
`preference_at`과 실제 `active`로 확인하며, 대시보드는 확인 뒤에만 완료를 표시한다.
기존 서버가 살아 있으면 소켓 상대의 사용자와 실제 PID, 시작 시각을 확인해 대화를 유지한다.
상태 파일의 PID가 유실돼도 소켓에서 복구하며 다른 프로세스로 재사용된 PID는 인계받지 않는다.
다시 연결한 감독은 서버가 쓰던 계정을 그대로 이어받고 다시 로그인하지 않는다. 로그인하면
열린 모든 대화의 MCP 서버가 다시 시작되고, 토큰 갱신 요청은 어느 연결에나 가기 때문이다
(0.169.0 소스 `app-server/src/outgoing_message.rs`). 감독 프로세스의 SIGTERM 종료나
상태 저장 실패는 공유 서버를 종료하지 않는다. 서버 시작 실패와 명시적인 서버 종료만
소유한 서버 프로세스를 내린다.

```sh
codex                            # 세션 중 자동 전환 활성화
codex resume --last              # 자동 전환 세션의 대화 계속
codex --account-status           # 사용률, 초기화 시각, 마지막 조회, 현재 계정
CODEX_ACCOUNT=company codex      # 회사 고정, 자동 전환 없음
CODEX_ACCOUNT=personal codex     # 개인 고정, 자동 전환 없음
```

## 전환과 초기화

- 사용량을 조회하는 같은 주기(1~9분)에 `account/read`로 서버가 실제 사용하는 계정도 확인한다.
  사용량 조회 성공이나 자동 전환 여부와 관계없이, 다른 연결에서 바꾼 계정도 `active`에 반영하고
  `account_observed_at`에 확인 시각을 남긴다. 이전에 확인한 계정과 다르면
  `last_external_change`에 변경을 기록한다. 감지 후에도 기존 우선순위와 90% 기준을 적용한다.
  이 조회는 로그인이나 토큰 갱신을 요청하지 않는다. 계정을 확인하지 못하거나 등록된
  두 계정 밖이면 `active`를 비우고 자동 전환을 보류하며 상태에는 `unknown`으로 표시한다.
- 두 계정의 사용량을 공식 `account/rateLimits/read`로 확인한다. 간격은 지금 쓰는 계정의
  사용률이 기준(90%)에서 30%p 이상 떨어져 있으면 9분, 15%p 이상이면 5분, 5%p 이상이면
  2분, 그보다 가까우면 1분이다(Claude 전환기와 같은 규칙).
- 알려진 초기화 시각이 더 빠르면 그 직후 다시 조회한다.
- 한도별 사용률·초기화 시각·조회 시각을 `~/.codex-auto/account-switcher.json`에 저장한다.
- 초기화 예정 시각이 지났다는 이유만으로 사용률을 0으로 바꾸지 않는다.
  실제 조회에서 다음 사용 기간으로 넘어간 것을 확인하면 `last_reset_confirmed_at`과
  `previous_resets_at`도 기록한다. 재시작 후에도 이전 기록을 사용한다.
- 회사가 다시 90% 미만이 되면 회사로 돌아간다. 조회 실패 시 이전 사용량을 새 정보로
  간주하지 않고 기존 계정을 유지한다. 상태 명령에는 조회 실패 여부를 표시한다.
- 전환 대상이 바뀌면 자동 서버의 모든 열린 대화가 쉬는지 확인한다.
  대상 계정의 사용량을 전환 직전에 다시 확인하며, 90% 이상이거나 조회 실패면 현재 로그인을 유지한다.
  실행 중인 응답·도구·승인 대기가 있으면 전환을 보류하고 2초부터 최대 30초까지
  간격을 늘려 다시 확인한다. 새 수동 선택 요청과 대상 변경은 이 대기 간격을 초기화한다.
  모델 응답을 받는 도중에 인증을 바꾸면 그 턴이 「application network permission was
  revoked」로 실패하고 대화가 `systemError`가 되기 때문이다(0.168.0, 2026-11-13 실측).
  `systemError`로 멈춘 대화는 아무것도 실행하지 않으므로 기다리지 않는다.
  90%는 엄격한 실시간 차단선이 아니다.
- 전환한 계정이 90% 미만이면, 마지막 턴이 사용 한도(`usageLimitExceeded`)로 실패한
  대화마다 「이어서 해줘」 턴을 한 번 시작한다. 사용자가 그 뒤에 이미 입력한 대화는
  건드리지 않는다. 그 턴의 화면 표시와 명령 승인 요청은 대화를 연 터미널로 간다.
  하위 에이전트(`parentThreadId`가 있는 대화)는 건너뛴다. 서버가 하위 에이전트의
  `turn/start`를 오류로 거부하고, 부모가 이어서 하면서 하위 에이전트를 다시 움직인다
  (0.169.0, 2026-11-18 실측).
- 감독이 서버와 맺은 연결은 알림을 하나도 받지 않는다(`initialize`의
  `optOutNotificationMethods`). 서버는 자기가 만든 대화(하위 에이전트)를 그때 붙어 있는
  모든 연결에 구독시킨다(0.169.0 소스 `app-server/src/lib.rs`). 2026-11-18에는 한 턴에서
  파일 84MB를 추가한 하위 에이전트의 `turn/diff/updated`(턴 전체 diff)가 16MiB 프레임
  한도를 넘어 감독의 수신 스레드가 끝났고, 그 뒤 모든 요청이 30초 시간 초과로 끝나
  회사 한도(100%)에서도 전환되지 않았다.
- 수신이 끝난 연결은 실제 소켓을 즉시 닫아 파일 descriptor를 회수한다. 감독은 60초마다
  자신의 유휴 구독 정리를 시작하고, 한 대화씩 최대 2초 예산으로 처리한다.
  남은 대화는 다음 2초 주기에 이어서 확인한다. 실행 중인 턴과 백그라운드 명령이 있는 대화는 유지한다.
  알림 opt-out만으로는 구독이 해제되지 않는다. 계정 사용량 조회가 실패해도 이 정리는 계속한다.
  끊긴 감독 연결은 같은 서버에 재연결하며 서버 재시작이나 재로그인을 하지 않는다.
- 서비스 준비 여부는 PID의 시작 시각과 120초 이내 heartbeat를 함께 확인한다.
  인증 갱신 실패 연결은 폐기하고, 동시에 대기한 갱신 요청은 한 번의 성공 결과를 공유한다.

## 실행 구조

`~/.local/bin/codex`는 이 디렉터리의 `launcher.py`를 가리킨다. 실제 CLI는
`/opt/homebrew/bin/codex`다. 최초 실행 시 백그라운드 감독 프로세스를 시작하고,
같은 사용자 전용 Unix 소켓으로 공식 Codex 터미널을 연결한다. 추가 패키지는 없다.
감독은 사용자 launchd 작업 `local.codex-account-switcher`로 등록한다. 감독이 종료되면
launchd가 최소 10초 간격으로 다시 시작하고 기존 공유 서버에 연결한다.
이미 등록된 작업과 진행 중인 대화는 새 터미널 실행으로 재시작하지 않는다.

감독이 새 공유 서버를 띄울 때는 Homebrew가 설치한 Codex 패키지 전체를
`~/.codex-auto/app-server-packages/<버전>/`에 보관하고 그 안의 실행 파일로 서버를 시작한다.
Homebrew가 업그레이드로 이전 버전을 지워도 이미 열린 대화와 `codex resume`은
같은 서버에서 원래 버전의 `codex-code-mode-host`와 리소스를 사용한다.
다음에 새 공유 서버가 시작되면 설치된 버전의 복사를 마친 뒤 이전 보관본을 정리한다.
이 변경을 적용하기 전에 Caskroom 경로에서 시작한 서버에는 다음 서버 시작부터 적용된다.

새 자동 터미널과 `codex resume`은 공유 서버가 연결 시 알려 준 버전의 CLI를 실행한다.
예를 들어 Homebrew가 0.170.0으로 올라가도 실행 중인 서버가 0.169.0이면 보관된
0.169.0 CLI를 쓴다. 보관 기능 도입 전에 시작한 서버는 Homebrew에 남은 같은 버전을 쓴다.
서버에 맞춰 설치 버전과 다른 CLI를 실행하는 동안에는 시작할 때 업데이트 확인을 건너뛴다.
Homebrew가 이미 설치한 버전을 그 터미널에서 다시 설치하라는 안내가 반복되는 것을 막는다.
감독은 15초 주기로 로컬 Homebrew 설치 경로와 서버가 보고한 버전을 대조한다.
버전이 다르면 임시 홈에서 새 패키지의 서버가 기동되는지 확인한다. 실행 중인 턴,
백그라운드 터미널, 작업 큐, 활성 goal, 메모리에만 있는 ephemeral 대화가 있으면 기다린다.
교체할 수 있으면 Codex의 SIGHUP으로 마지막에 접수한 턴까지 마무리하고 같은 소켓에서
새 서버를 띄워 기존 계정을 복원한다. 새로 여는 터미널은 이 서버의 버전을 사용한다.
기존 터미널의 실행 파일 버전은 그 터미널을 다시 열 때 바뀐다.
버전이 같으면 새 터미널은 Homebrew 실행 파일을 사용해 다음 업데이트를 확인한다.
서버 버전을 확인할 수 없거나 같은 버전의 실행 파일이 없으면 설치된 CLI로 연결하며
이 경우 Codex가 버전 경고를 표시할 수 있다.

일반 실행에는 외부 릴리스 조회를 추가하지 않는다. zsh에서 `codex update` 또는
`claude update`를 실행하면 Homebrew Codex와 네이티브 Claude의 공식 업데이트 명령을
각각 실행하고 Codex 공유 서버 적용 결과를 출력한다. 사용 중이면 대기로 표시하며
`codex --account-status`에서 적용 상태를 확인할 수 있다. Claude 전환기는 기존 설치
심링크를 따라 새 바이너리의 호환성을 확인한다. 두 명령의 zsh 연결은
`mac/ai-cli-update.zsh`이며 Oh My Zsh custom 디렉터리에 심링크로 설치한다.

실행기와 새 공유 서버 시작 경로에서 열린 파일 soft limit을 4096까지 높인다.
`--no-daemon`과 명시적인 `CODEX_HOME`도 실행기를 통과하면 적용된다.
기존 hard limit은 유지하고, 이미 더 높은 soft limit도 낮추지 않는다. macOS 기본값 256에서는
여러 대화의 MCP 파이프·소켓이 한 서버에 모여 `Too many open files`가 발생할 수 있다.
이미 실행 중인 서버에 재연결할 때는 그 서버의 한도가 바뀌지 않으므로 재시작이 필요하다.
이 설정은 프로세스 시작 용량 보완이며 Codex 내부의 자원 누수 여부를 판정하지 않는다.

원래 로그인은 회사 `~/.codex-work`, 개인 `~/.codex`에 각각 남는다.
한 프로필을 읽지 못해도 확인 가능한 현재 서버 연결은 유지한다. 실패한 프로필은 다음
사용량 조회에서 다시 읽는다. 두 프로필이 같은 workspace이면 자동 전환 후보에서 제외한다.
공식 Codex가 각 로그인의 갱신을 담당한다. 자동 서버에는 `chatgptAuthTokens` 인증으로 선택된
자격증명을 메모리에 전달하며, 원래 인증 파일을 덮어쓰거나 자동 서버에 복사하지 않는다.
사용량 응답의 실제 계정 ID를 확인한 뒤 전환 성공으로 기록한다.

전체 유휴 검사는 백그라운드에서 진행한다. 30초 단위로 다음 대화부터 이어서 검사하며
감독은 상태와 수동 요청을 계속 확인한다. 5분 이상 소비되지 않은 검사 결과는 다시 확인한다.
전환 직전 대상 계정의 한도를 확인하고, 검사 도중 새 활동이 관측되면 전환을 미룬다. 서버가 유휴 확인과 인증 교체를 하나의 원자적 연산으로 제공하지 않아
마지막 확인 직후 새 턴이 시작하는 경쟁까지 제거하지는 못한다.
한도 초과 대화의 이어하기 점검도 백그라운드에서 처리한다. 대화 사이에서 30초 예산을
확인하며 순회 진행을 보존한다. 시작한 대화는 각 RPC의 30초 제한 안에서 마친 뒤 넘어간다.
명시적으로 거절되거나 전송되지 않은 요청은 재시도한다. 전송 후 응답을 잃은 요청은
중복 제출하지 않고 `uncertain_continuation_count`에 표시한다. 이후 새 턴이나 진행 상태가
관측되면 표시를 해제한다. 계속 같은 실패 턴으로 남으면 해당 대화에서 수동 확인이 필요하다.

이 인증 방식은 공식 문서의 실험적 app-server 인터페이스다. 설치된 0.167.2의
스키마에는 내부용이라는 표시도 있으므로 안정적인 호환성 계약으로 간주하지 않는다.
버전 변경 뒤 인터페이스가 거부되면 자동 실행을 중단하고 고정 계정 실행을 안내한다.
2026-11-13에 실제 회사 → 개인 → 회사 인증 전환, 각 계정 사용량 조회,
모델 호출 없는 동일한 임시 대화 유지, Unix 소켓 연결을 검증했다. 같은 날 0.168.0
시험 서버에서 한 대화에 회사 → 개인 → 회사 순서로 모델 턴 세 번을 돌려 모두 성공했다
(앞 계정의 암호화 추론 항목이 든 기록 포함). 감독 연결이 시작한 턴의 알림·승인 요청이
대화를 연 연결로 가는 것과, 한도 초과로 끝난 실제 기록 사본에서 「이어서 해줘」가 한 번만
시작되는 것도 확인했다.

자동 세션의 기록은 `~/.codex-auto`에 저장된다. 회사가 우선이므로 설정은 회사 홈 설정
(`config.toml`, 회사 MCP·모델 포함)을 링크하고, 스킬·플러그인 등은
`~/.codex`를 공유한다. 회사 설정의 워크스페이스 고정은 자동 서버를 띄울 때만
`-c forced_chatgpt_workspace_id=""`로 풀어 개인 계정으로도 바꿀 수 있게 한다(고정이 있으면
개인 로그인이 거부되고, 붙은 터미널은 고정을 검사하지 않는다. 0.168.0, 2026-11-13 실측).
원격 터미널은 폴더를 보내지 않으면 서버의 폴더에서 돌기 때문에, 실행기가 실행한 터미널의
폴더를 `-C`로 넘긴다. 같은 이유로 셸 명령도 서버에서 돌아 터미널의 cmux 탭 환경을 물려받지
못하므로, cmux 탭에서 실행하면 탭 ID(`CMUX_SURFACE_ID`), 탭의 cmux 소켓 권한(`CMUX_SOCKET_CAPABILITY`,
cmux가 띄우지 않은 서버 쪽 프로세스는 이것이 있어야 cmux에 붙는다), 실행기 pid(`CMUX_CODEX_PID`,
execve로 터미널 pid가 된다)를 `-c shell_environment_policy.set.*`로 넘긴다. refresh-session이 이 값으로
같은 탭에서 세션을 다시 띄운다. 0.169.0 터미널은 이 설정을 대화 시작·재개 요청에 담고(소스
`tui/src/app_server_session.rs`), 서버는 그 대화의 셸 명령 환경에 넣는다(2026-11-16 임시 대화로 확인).
이미 서버에 올라와 있는 대화를 다른 터미널이 붙어 볼 때(에이전트 목록 선택 등)는 설정을 다시 보내지
않으므로 처음 연 터미널의 값이 남는다.
모든 자동 세션은 같은 서버와 활성 계정을 사용한다. 이미 열려 있던 기존
세션은 전환 대상에 포함되지 않는다. 이전 개인·회사 프로필의 대화는 각각
`CODEX_ACCOUNT=personal codex resume` 또는 `CODEX_ACCOUNT=company codex resume`으로 연다.

`exec`, `review` 등 비대화형 명령은 시작할 때만 계정을 선택한다. `login`, `logout`,
`mcp`, `plugin`, `queue`, `archive`, `delete` 등 관리 명령은 회사를 기본으로 사용한다.
명시적인 `CODEX_HOME`, `--remote`, `--no-daemon`은 자동 서버를 사용하지 않는다.
`CODEX_HOME="$HOME/.codex-work" codex`로 연 세션은 회사 계정에 고정되어 전환되지
않는다. 회사 우선 자동 전환은 그냥 `codex`로 연다.
자동 기록에 관리 명령을 적용할 때는 `CODEX_HOME="$HOME/.codex-auto"`를 명시한다.

## 검증

### 열린 터미널의 유휴 자원 회수

새 자동 세션은 터미널마다 작은 로컬 프록시를 거친다. 기본 15분 동안 활동이 없고,
대화가 `idle`이며 실행 중인 백그라운드 명령·미완료 goal·대기 입력이 없으면 프록시가
자신의 구독을 해제한다. 다른 연결의 구독도 없으면 공식 서버가 기본 60초 유예 뒤
대화 런타임과 해당 MCP를 회수한다. 터미널과 입력 초안은 유지하고, 다음 요청 전에
같은 thread ID로 재개한다. 기록 파일을 삭제하거나 서버를 재시작하지 않는다.

기록이 없는 대화, ephemeral 대화, realtime, 복원할 수 없는 설정·동적 도구·환경이 있는
대화는 유지한다. 자식의 미전달 메시지와 환경을 가진 부모도 유지한다. 기존 기록을
`resume`·`fork`로 연 최상위 대화는 숨은 자식 상태를 확인할 수 없어 자동 회수하지 않는다.
하위 대화는 부모를 유지한 채 유휴 상태에서 회수하며, 다시 실행되면 구독을 복구한다.
이 제한은 실행 중인 작업과 메모리에만 있는 상태를 보존하기 위한 것이다.

```sh
codex                              # 새 자동 세션: 15분 유휴 검사
CODEX_IDLE_SECONDS=1800 codex        # 이 터미널은 30분
CODEX_IDLE_SECONDS=0 codex           # 이 터미널은 유휴 프록시 사용 안 함
```

이미 열린 터미널, `--no-daemon`, 고정 계정, 명시적 `CODEX_HOME`·`--remote`에는
이 프록시가 소급 적용되지 않는다. 연결을 추가로 붙인 도구가 구독을 유지하면 회수도
기다린다. 감독은 자신의 유휴 구독을 별도로 60초마다 반환한다.

프록시는 터미널 프로세스가 살아 있는 동안 같은 Unix 소켓으로 재접속을 받는다.
서버 연결이 끊기면 해당 연결만 닫고, Codex TUI의 새 `initialize`·`thread/resume`로
복구한다. 이전 연결의 요청을 프록시가 다시 보내지 않는다. 터미널 종료 시 프록시와
임시 소켓도 정리한다.

Codex 0.169.0 TUI의 자동 재접속 시한은 120초다. 서버가 그 안에 돌아와야 자동 복구되며,
이미 `Reconnect failed`가 된 화면은 입력 초안을 복사한 뒤 `Ctrl+C`로 종료하고
`codex resume`으로 기존 대화를 선택한다. 이 수정은 새로 실행한 터미널부터 적용된다.

### 큰 알림을 받을 때의 CPU·메모리

WebSocket은 한 번에 최대 64 KiB를 받고 조각을 한 번만 합친다. 불변 `bytes`에 수신
조각을 반복 연결하던 방식은 큰 diff에서 크기의 제곱에 비례해 복사 비용이 커졌다.
작은 프레임은 4 KiB 단위로 미리 읽어 소켓 호출을 줄이고, fragmentation 누적 한도는
본문을 받기 전에 확인한다. 길이가 0인 조각도 포함해 메시지당 조각은 4,096개까지 허용한다.

프록시는 JSON을 한 번 해석하고 원문과 작은 라우팅 정보만 대기열에 보관한다. 전달 후에는
메시지 참조를 해제해 다음 알림이 없어도 큰 diff가 남지 않는다. 대기열은 원문 256 MiB와
4,096개 메시지까지 허용하며, 초과하면 양쪽 연결을 닫아 TUI가 재접속하게 한다. 내부 RPC
응답은 이 대기열을 우회한다. 불확실한 요청은 자동 재전송하지 않는다.
응답 대기 요청도 양방향 합계 4,096개와 원문 크기 합계 256 MiB까지 허용한다.
서버가 보낸 요청의 동시 처리 스레드는 8개까지이며, 상한을 넘으면 연결을 종료한다.
쓰기가 막힌 시간도 RPC 제한시간에 포함한다. 잘못된 WebSocket 연결 요청은 해당 연결만 닫는다.

유휴 검사는 응답을 기다리는 동안에도 사용자 요청을 전달하며, 입력·승인·상태가 바뀐 대화는
오래된 검사 결과로 회수하지 않는다. 한 검사에서 loaded 목록의 모든 페이지와 부모 관계를
재사용한다. 마스킹은 Python의 바이트별 반복 대신 `bytes.translate`로 처리한다.
상태 알림에서 처음 발견한 대화의 조회도 사용자 입력 전달을 막지 않는다.
삭제된 대화는 복원 정보를 제거하며, 의도적으로 구독을 놓은 대화는 재개 정보를 유지한다.

2026-11-19 Python 3.10 격리 측정: 8 MiB 마스킹 CPU 0.419초 → 0.0075초.
50개 유휴 대화 fixture의 RPC는 2,850회 → 401회다. 32 MiB 실제 proxy 전달 후
살아 있는 Python 할당은 1.914 MiB → 1.922 MiB였다(RSS 163 MiB는 할당자 보유분 포함).
이는 아래 2026-11-18 측정과 별도의 실험이다.

각 임시 `tui.sock` 옆 `tui.json`에 PID·소유 터미널 PID·시작 시각·실행 소스 SHA-256을 기록한다.
소스만 바꿔도 기존 Python 프로세스가 바뀌지는 않는다. 기존 터미널용으로 별도 실행한 proxy도
macOS의 프로세스 종료 알림으로 그 터미널의 수명을 따른다. 공유 app-server는 재시작할 필요가 없다.
감독 상태는 변경 시 즉시 저장하고, 변화가 없어도 30초마다 heartbeat를 저장한다.

2026-11-18 Python 3.10 격리 비교(32 MiB, 실제 모델 호출 없음):

| 측정 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 16 KiB 조각 수신 CPU 시간 | 9.67초 | 0.034초 |
| 실제 프록시 알림 전달 시간 | 29.33초 | 0.80초 |
| 전달 뒤 프록시 RSS | 2,115 MiB | 160 MiB |

수정 후 별도 `tracemalloc` 측정의 살아 있는 Python 할당은 전달 전 1.795 MiB,
전달 후 1.801 MiB였다. RSS에는 할당자가 보유한 메모리가 포함되므로 살아 있는 메시지와
구분한다. 위 수치는 이 로컬 재현의 비교값이며 전체 장비·공용 서버의 사용량이 아니다.

```sh
python3 codex/account-switcher/probe_transport.py --mib 32
python3 codex/account-switcher/probe_transport.py --proxy --mib 32
python3 codex/account-switcher/probe_transport.py --proxy --trace --mib 32
# 다른 worktree와 비교할 때 --source /경로/codex/account-switcher 사용
```

### 불필요한 로컬 MCP 줄이기

데이터 조회나 Chrome 도구가 필요 없는 독립 코딩 세션에서만 다음처럼 끈다.
전역 설정과 다른 대화에는 영향을 주지 않는다.

```sh
codex --no-daemon \
  -c 'plugins."<data-plugin>@<marketplace>".enabled=false' \
  -c 'mcp_servers.chrome-devtools.enabled=false'
```

데이터 플러그인의 로컬 DataHub·Redash 실행과 Chrome 브리지 클라이언트를 줄이는 설정이다.
연결된 원격 앱은 그 자체로 로컬 MCP 자식 프로세스를 만드는 것은 아니다.
Chrome 브리지의 공용 데몬은 이미 공유되므로 다른 대화가 쓰는 데몬을 종료하지 않는다.

`codex --no-daemon --enable mcp_lazy_stdio_startup`도 선택할 수 있다. 0.169.0의
실험 기능이며, 격리 실험에서는 첫 도구 목록 수집 때 MCP를 시작한 뒤 캐시가 있는
후속 대화에서는 실제 도구 호출까지 시작을 미뤘다. 모든 플러그인·필수 MCP의 시작을
미룬다고 보장하지 않는다. 도구 설명의 지연 노출과 프로세스의 지연 시작은 별개다.
`mcp_connection_sharing`도 실험 기능이고 서버 프로토콜 지원이 필요하므로,
기존 stdio 서버를 플래그 하나로 전부 공유할 수 있다고 가정하지 않는다.
