# /dev-plan -- 개발 계획 및 작업 분할

개발 작업을 PR 단위로 분할하고, 의존성 기반 순서와 일정을 산정한다.

## 트리거 조건

### 명시적 트리거
- "개발계획 짜자", "작업 나누자", "일정 산정해줘" 등 직접 요청

### 자동 트리거 (CRITICAL)
- 사용자가 **작업 분할 없이 바로 개발에 착수**하려 할 때 (예: "이거 구현해줘", "코딩 시작하자")
- 아래 조건이 **모두** 해당되면 자동 발동:
  1. 현재 세션에서 `/dev-plan`이 아직 실행되지 않았음
  2. 구현할 작업이 **단일 파일 수정 수준을 넘는** 규모
  3. 기존에 작업 분할이 완료된 계획이 없음
- 자동 트리거 시 사용자에게 확인:
  > "작업이 여러 PR로 나뉠 수 있는 규모로 보입니다. 먼저 `/dev-plan`으로 작업을 분할하고 일정을 산정할까요? (Y/N)"
- 사용자가 N을 선택하면 즉시 구현으로 진행한다.

## 사전 준비

### Step 0: PRD 확인

사용자에게 PRD(Product Requirements Document)를 요청한다:
> "관련 PRD 문서가 있나요? 있으면 경로나 URL을 알려주세요."

PRD가 있으면 문서를 읽어 요구사항을 파악한다.
PRD가 없으면 사용자에게 구현할 기능/변경사항을 구두로 설명받는다.

### Step 1: Linear 카드 확인

관련 Linear 이슈가 있는지 확인한다:
> "관련 Linear 이슈가 있나요? 있으면 이슈 ID를 알려주세요."

이슈가 있으면 Linear API (`~/.claude/linear_api_key`)로 상세 조회한다.
이슈가 없으면 작업 분할 완료 후 생성 여부를 물어본다 (Step 7에서 처리).

### Step 2: 코드베이스 파악

작업 대상 레포지토리와 관련 코드를 파악한다:
- 사용자에게 대상 레포 확인
- 관련 코드 구조, 기존 패턴, 아키텍처 확인
- 변경이 필요한 레이어/모듈 식별

## 작업 분할

### Step 3: 작업 분해

PRD/요구사항과 코드베이스 분석을 기반으로 작업을 분해한다.

#### 분할 원칙

1. **PR 크기 목표: 100~200줄** (diff 기준, 테스트 제외)
   - 200줄 초과 예상 시 더 쪼갠다
   - 같은 레이어의 작업을 너무 잘게 쪼개야 할 것 같으면 사용자에게 확인

2. **아키텍처 원칙 기반 분할**
   - **DDD**: 도메인 모델 -> 리포지토리 -> 서비스 -> 컨트롤러 순
   - **클린 아키텍처**: 내부 레이어(Entity, UseCase)부터 외부 레이어로
   - **레이어드**: 하위 레이어부터 상위 레이어로
   - **CQS**: Command와 Query를 별도 PR로
   - **KISS / YAGNI**: 현재 필요한 것만 구현
   - **TDD**: 각 PR에 테스트 포함. 테스트 먼저 작성

3. **PR 단위 기준**
   - 하나의 PR은 하나의 논리적 변경
   - 리팩토링과 기능 추가를 같은 PR에 섞지 않는다
   - DB 마이그레이션은 별도 PR
   - 설정/인프라 변경은 별도 PR

4. **PR 간 독립성 확보 (CRITICAL)**
   - 각 PR은 가능한 한 **독립적으로 구현/리뷰/QA 가능**
   - PR-A 리뷰/QA 중 PR-B 구현 시작 가능해야 함
   - 인터페이스/계약을 먼저 정의, 각 PR이 독립 구현
   - 독립 분할이 어려운 경우 사용자에게 확인

#### 분할 출력 형식

```markdown
### PR-{N}: {PR 제목}

- **설명**: 이 PR에서 무엇을 하는지 1~2줄
- **변경 범위**: 수정/생성할 파일 목록 (예상)
- **예상 diff**: ~{N}줄
- **의존성**: PR-{M}에 의존 (없으면 "없음")
- **아키텍처 패턴**: 적용되는 패턴
- **테스트**: 필요한 테스트 종류 (단위/통합/E2E)
- **작업 유형**: 고가속/중가속/저가속
- **일정 산정** (AI 에이전트 기반):
  - 코드 구현 (지시+생성+리뷰): {시간} (전통적 {시간} x {승수})
  - 자체 QA (AI 테스트+검증): {시간}
  - 코드 리뷰 대기 + 피드백 반영: {시간}
  - QA: {시간}
  - **소계**: {시간}
```

### Step 4: 의존성 분석 및 순서 결정

1. **의존성 기반 정렬**: A가 B에 의존하면 B를 먼저
2. **의존성이 없는 작업끼리**: 의미 단위로 그룹핑, 작업 규모가 작은 것부터
3. **의존성 그래프 시각화**: Mermaid 다이어그램으로 표시

### Step 5: 전체 일정 산정

**정량 상세 기준은 `references/estimation.md`를 따른다** (요일별 가용 시간, AI 승수표·시간 구성 비율·산정 근거/출처, 단계별 승수, 파이프라인, 출력 템플릿). 핵심 요약:

- **하루 가용 시간**(§1): 월5.5/화6/수6/목6/금5h, 주 28.5h. 변수 버퍼 1.5h/일.
- **캘린더 확인 (CRITICAL)**: Google Calendar MCP가 있으면 작업 기간 이벤트 조회(공휴일·회사 휴일·연차/휴가·임시 미팅·블로킹된 시간대). 없으면 사용자에게 직접 받음. 공휴일/휴가는 영업일 제외, 추가 미팅 있는 날은 가용 시간 추가 차감.
- **AI 승수 (CRITICAL)**: 고 0.4~0.5x / 중 0.6~0.7x / 저 0.8~0.9x. 자체 QA 0.5~0.6x, 피드백 반영 1차 0.4x·추가 라운드 0.5x(@30%), 리뷰/QA 대기 0.5~1영업일. FE는 꼼꼼/빠른(×0.7) 두 값 병기. 보수적 산정 근거(METR 19%↓ 등)·출처는 §2.
- **파이프라인 (CRITICAL)**: 리뷰/QA 대기 중 다음 PR 병렬 진행, 컨텍스트 스위칭 PR당 30분. 상세 §3.

### Step 6: 사용자 확인

전체 계획을 출력한 뒤:
> "작업 분할과 일정이 적절한가요? 수정할 부분이 있으면 알려주세요."

### Step 7: Linear 카드 생성

사용자 확인 완료 후 Linear 이슈 생성 여부를 묻는다.
- 기존 이슈가 있으면: 각 PR을 하위 이슈로 생성할지 확인
- 없으면: 상위 이슈 + 하위 이슈 생성할지 확인
- **반드시 사용자 확인 후** 진행

Linear GraphQL API 호출: `~/.claude/linear_api_key` 파일의 API 키 사용.

## Step 10: 자가 개선 (Self-improvement)

계획 완료 후, 다음 단계(plan-review)로 넘어가기 전에 학습 내용을 반영한다.

### 업데이트 대상
1. **일정 승수 보정** — 이전 작업의 산정 vs 실제 소요 비교, 20%+ 오차 시 `references/estimation.md`의 승수 표 조정
2. **분할 패턴** — 사용자가 합치거나 더 쪼갠 경우 분할 원칙에 반영
3. **AGENTS.md** — 새로 발견된 워크플로우 개선점

업데이트할 내용이 있으면 1줄씩 나열 후 자동 반영. 없으면 스킵.

## 주의사항

- **이 스킬은 계획만 세운다. 코드를 작성하지 않는다.**
- Linear 이슈 생성은 **반드시 사용자 확인 후** 진행한다.
- 작업 규모가 PR 1개로 충분한 경우, 분할하지 않고 바로 일정만 산정한다.
- 같은 레이어의 작업을 쪼개야 하는지 애매하면 항상 사용자에게 물어본다.
