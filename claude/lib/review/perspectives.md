diff를 아래 카테고리의 관점으로 검증한다. `~/.claude/lib/review/tool/index.md`를 Read하고, 그 목록에서 diff가 쓰는 도구의 모듈을 Read해 도구 이름을 카테고리로 더한다.

## 조용한 실패와 기본값

- 실제로 발생 가능한 예외와 필요한 복구·전달 동작을 확인해 불필요한 예외 처리를 지운다. 순수 계산이나 상수 조회라는 이유만으로 예외가 없다고 가정하지 않는다.
- 입력(요청, 메시지, 파일)에 필수 값이 빠지면 에러로 멈춘다.
- 대상 목록이 비면 전체로 넓히는 대신 아무것도 하지 않거나 거절한다.
- 빈 입력을 구분자로 나눈 결과(`[""]`)는 빈 목록으로 다룬다.
- 필수 enum 필드에 빈 값(`''`, `UNSPECIFIED`)이 오면 검증에서 거절한다.
- 범위의 최솟값과 최댓값으로 따로 조회하는 코드는 두 값이 같으면 한 번만 조회한다.
- 호출자가 다르게 처리해야 하는 데이터 없음·불일치·처리 실패의 의미를 보존한다. `~/.claude/lib/coding/types.md`에 따라 직접적인 분기·구체적인 결과·enum을 비교하고, 오류를 불완전한 성공값이나 이유 없는 boolean으로 숨기지 않는지는 `~/.claude/lib/coding/errors.md`로 판정한다.
- 컬럼을 더는 쓰지 않게 바꿔도, 그 컬럼에 이미 쌓인 값을 읽던 조회(옛 컬럼 값을 더하는 합계)는 그 값을 계속 읽는다.

## 트랜잭션·동시성·순서

- 커밋 뒤에 다른 시스템을 부르면, 호출 실패를 성공 응답으로 덮는 대신 outbox(보낼 요청을 같은 트랜잭션 안 테이블에 남기고 커밋 뒤 따로 보냄)나 보상 처리(먼저 만든 리소스를 지움)를 쓴다.
- 조회한 결과로 행을 지울 때는 SELECT 뒤 DELETE 대신 조건을 건 DELETE 한 번이나 잠금을 쓴다.
- 여러 개 가운데 하나를 고를 때는 순서가 정해진 결과에서 고르고, 값이 겹칠 수 있는 컬럼으로 정렬하면(`ORDER BY created_at`) 보조 키(id)를 더한다.
- 캐시·락 키의 단위(계정, 사용자, 세션)는 한 계정을 여러 사람이 함께 써도 각자 자기 캐시만 읽고 자기 작업만 잠그는 단위로 정한다.

## 금액

- 금액을 계산하는 코드는 소수점 자릿수, 반올림 방식, 통화를 정해 둔다.
- 환율을 바꾸면 환율을 저장한 뒤 그 환율로 계산한 금액을 다시 계산한다.

## 기존 코드와의 일관성

- 새로 만들려는 함수·플래그·조건식과 같은 일을 하는 기존 함수나 도메인 메서드가 있으면(Grep으로 찾는다) 그것을 쓴다.
- 같은 꼴로 나란히 있는 설정·분기·목록 항목 가운데 일부를 바꾸거나 새 항목을 더하면, 같은 변경이 필요한 나머지 항목도 함께 바꾼다.
- 이번 변경으로 쓰는 곳이 없어진 함수·필드는 deprecated 표시 대신 같은 PR에서 지운다.

## 데이터베이스·스키마

- 새 쿼리의 조건에는 그 쿼리가 쓸 복합 인덱스의 첫 컬럼을 넣는다.
- 새 복합 인덱스는 값 종류가 많은 컬럼을 앞에, 값 종류가 적은 컬럼(상태, 참거짓)을 뒤에 둔다.
- 지울 행 수가 정해지지 않은 DELETE는 조건만 건 DELETE 한 번 대신 정해진 크기씩 나눠 지운다.
- ORM의 DB 연결 설정(풀 크기, 연결 유지 시간, 타임아웃)을 바꾸면 그 연결을 쓰는 API에서 확인한 결과를 PR에 적는다.
- DB enum 컬럼이 받는 값을 코드에 더하면 같은 PR에 마이그레이션을 넣는다.
- API 응답이나 저장하는 JSON은 타입 없는 dict·map 대신 필드 타입이 있는 스키마(DTO)로 내보낸다.
- union 타입에는 어느 꼴인지 가르는 구분 필드를 둔다.

## 로그·메트릭

- 루프 안에서 항목마다 남기는 debug 로그는 머지 전에 지운다.
- info 로그에 `[DEBUG]` 같은 접두어가 붙어 있으면, 테스트용이면 지우고 아니면 debug 레벨로 바꾼다.
- 기존 로그에 샘플링이 걸려 있으면 같은 종류의 로그를 새로 남기는 곳에도 같은 샘플링을 건다.
- 한 사건은 여러 줄로 나누는 대신 한 줄 로그에 필드로 묶고, 요청 추적 id(`correlation_id`)를 넣는다.
- 새 메트릭 이름은 같은 대상을 재는 기존 메트릭의 단어와 단어 순서를 따른다(기존이 `daily_total`이면 `total_daily` 대신 `daily_` 꼴).
- 기존 메트릭과 같은 값을 재야 하면 새 메트릭 대신 기존 메트릭을 쓴다.
- 새 메트릭을 더하면 그 메트릭을 볼 알람이나 대시보드를 PR에 적는다.
- 메트릭 라벨에는 사용자 id·요청 id처럼 끝없이 늘어나는 값 대신 값 종류가 정해진 값(상태, 종류)을 넣는다.
- 새로 만든 배치, consumer, 다른 시스템 호출에는 성공·실패 수를 재는 메트릭을 단다.

## 설정과 생성 파일

- 환경(dev, staging, prod)마다 달라야 하는 값은 코드 상수 대신 환경 변수나 설정 파일에 둔다.
- 정의만 있고 읽는 곳이 없는 환경 변수는 지운다.
- 새 재시도 코드의 횟수·간격은 저장소의 기존 재시도 설정을 따른다.
- 테스트에서만 쓰는 패키지는 운영 의존성 대신 개발용 의존성(개발용 requirements 파일, `devDependencies`)에 더한다.
- 도구가 만든 산출물 디렉터리(`.playwright-mcp`)는 커밋하는 대신 `.gitignore`에 더한다.
- 도구가 만들고 업데이트 때 다시 쓰는 파일(`{도구} init`이 만든 템플릿)은 손으로 고치는 대신 도구 설정이나 따로 둔 파일에서 바꾼다.
- AGENTS.md·CLAUDE.md는 되돌릴 수 없는 명령(`rm -rf`, `git push --force`, 운영 DB 쓰기)을 에이전트가 실행하게 하는 대신 사람이 실행하게 둔다.
- diff의 JSON 파일은 파싱해 보고, 오류가 나면 그 줄 번호를 발견에 적는다.

## 배포

- 다른 서비스의 변경이 있어야 동작하는 diff면 그 서비스의 PR과 배포 순서(서버 → 게이트웨이 → 화면)를 PR 본문에 적는다.
- 공유 API 스펙 패키지의 버전을 바꾸면 스펙 저장소의 짝 PR을 함께 낸다.
- 여러 유형(상품 종류, 매체 종류)의 동작을 바꿀 때는 한 번에 바꾸는 대신 유형별로 나누거나 비율을 정해 차례로 적용한다.
- 배포 설정의 서비스 이름·환경 값은 PR이 바꾸려는 대상과 같게 쓴다.

## 변경 설명

- PR 본문에는 바뀐 파일·함수 나열 대신 바꾸는 이유를 적는다.
- 다른 회사 API를 새로 부르거나 부르는 방식을 바꾸면 그 회사 정책(호출 한도, 허용 용도)을 확인한 근거를 PR에 적는다.
- 쓰이지 않는 코드를 지우는 PR이면 그 PR 코멘트에 지운 코드를 더한 PR과 쓰이지 않게 된 PR(처음부터 안 쓰였으면 그 사실)을 적는다.

## 테스트

- 집계 코드를 바꾸면 빈 입력과 기간 경계(월 합계가 일 합계의 합과 같은지)를 확인하는 테스트를 둔다.
- 테스트는 호출 여부만 확인하는 대신 이름이나 docstring이 약속한 결과를 assert로 확인한다.
- 테스트는 결과를 인덱스(`result[0]`) 대신 id로 찾아 확인한다.
- 테스트 형식(함수별 테스트, 표 기반 테스트)은 그 파일이 이미 쓰는 형식을 따른다.

## 데이터 분석·머신러닝

- 같은 피처를 애플리케이션 코드와 SQL 두 곳에서 계산하면 두 결과가 같은지 확인하는 테스트나 쿼리를 둔다.
- 상위 K개나 임계값으로 거르는 평가 코드는, 대상이 K개보다 적을 때 빼는지 넣는지를 코드나 테스트로 정한다.
- 코드에 넣은 임계값·가중치 숫자는 정한 근거(실험 결과, 문서 링크)를 주석이나 PR에 적는다.

## 코드 위생

- 주석 처리한 코드는 지운다.
- 코드를 바꾸면 그 코드와 맞지 않게 된 주석도 고친다.
- base 브랜치에 이미 들어간 코드는 PR에서 뺀다.

## 성능

- 루프 안에서 매번 같은 값을 내는 계산은 루프 밖으로 옮긴다.
- 메모리에서 정렬·필터하는 목록이나 범위 조회는 건수 상한을 코드에 두거나, 운영에서 들어올 최대 건수를 PR에 적는다.
- 페이지마다 같은 집계를 다시 계산하는 대신 서버가 한 번 계산해 돌려준다.

## 변경 이력·과거 리뷰

- 변경된 줄의 원래 의도를 `git blame`과 `git log -L <시작>,<끝>:<파일>`로 거슬러 확인한다. 이번 변경이 그 의도를 되돌리거나 예전에 고친 버그를 다시 들이면, 그 커밋의 해시와 제목을 근거로 발견에 적는다.
- 같은 파일을 건드린 최근 PR을 `git log -n 10 --format='%h %s' -- <파일>`로 찾는다(커밋 제목의 `(#번호)`). 그 PR의 리뷰 코멘트를 `gh pr view <번호> --comments`와 `gh api repos/{owner}/{repo}/pulls/<번호>/comments`로 읽고, 그때 나온 문제가 이번 diff에도 해당하면 그 PR 링크를 근거로 발견에 적는다.

## 출력 형식

카테고리마다 발견이 있으면 `### {카테고리}: N건`과 `- [CRITICAL/INFO] file:line · 설명`을, 발견이 없으면 `### {카테고리}: PASS`나 `### {카테고리}: 해당 없음`을 쓴다.
