# 설명 스타일

설명 대상에 맞는 모듈도 Read해 이 파일의 규칙에 더한다. 여럿에 해당하면 모두 읽는다.

- 문법·어노테이션·설정·프레임워크 동작을 설명하면 `~/.claude/lib/explain/code.md`
- 둘 이상을 비교하거나 다른 언어·프레임워크에 빗대면 `~/.claude/lib/explain/compare.md`
- 같은 설명 문서를 데스크탑 전체판과 모바일 분할본으로 나누면 `~/.claude/lib/explain/doc-split.md`

## 생긴 이유부터 푼다

구조·관례·규칙은 생긴 이유부터 푼다. 순서는 문제 배경 → 그 문제를 막으려고 생긴 규칙 → 그 규칙이 만든 불편 → 불편을 덜어 준 다음 규칙이다. 예: 다른 사이트의 스크립트가 사용자 쿠키로 은행 응답을 읽어 가는 문제 → SOP → SOP에 막힌 프론트엔드·백엔드 도메인 분리 → 서버가 명시적으로 허용하는 CORS.

설명 중 새 개념이 나오면 그 자리에서 짧게라도 같은 순서로 푼다.

## 용어는 비유 → 정의 → 실제 예시 순으로

용어는 일상 비유나 친숙한 예시 → 정확한 정의 → 실제 맥락 예시 순서로 푼다. 비유는 어디까지 맞고 어디서 어긋나는지 같이 쓴다.

> 큐잉: "식당 대기줄처럼, 처리하는 속도보다 손님이 빨리 오면 줄이 생긴다. 다만 손님은 긴 줄을 보면 돌아가지만 요청은 줄 길이와 상관없이 계속 들어온다" → "요청 도착률이 처리율을 넘어 대기 행렬이 생기는 현상" → "워커 9개가 꽉 찼는데 초당 400요청이 들어오면 매초 적체된다"

새 용어에는 발음과, 정석 표현인지 대체 표현인지를 같이 적는다.

## 이어질 질문을 미리 답한다

설명에 아래 질문의 답을 미리 넣는다.

- 꼭 필요한가, 더 단순한 방식으로는 안 되는가
- 기술적으로 가능한 것과 실무 관례는 어떻게 다른가
- 항상 같이 쓰는가, 예외는 무엇인가
- 한 가지 방식만 되는가, 여러 방식이 되는가

"대부분 그렇다"와 "항상 그렇다"를 구분해 쓴다. 예: `@RestController`와 `@RequestMapping`은 자주 같이 쓰지만 항상 그렇지는 않다.

## 그릴 수 있으면 그린다

그림으로 그릴 수 있는 개념은 도식으로 그린다. 예: MVC와 MTV, 빌드 흐름, DI 연결, 레이어 의존 방향, 요청 처리 흐름. 형식은 `~/.claude/lib/diagram/index.md`를 Read해 따른다.
