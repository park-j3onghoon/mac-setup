- 문법·어노테이션·설정·프레임워크 동작을 설명하면, 코드 구조·설정이 왜 그런지 쓸 때는 표준·관례·프레임워크 제약·팀 커스텀 가운데 무엇인지 밝히고(예: `src/main/kotlin`은 기술적으로 바꿀 수 있지만 표준 구조이고, 역도메인 패키지 이름은 충돌을 막는 관례다), 언급한 어노테이션·설정·패턴에는 바로 짧은 예제 코드를 붙이며, 프레임워크가 내부에서 정확히 어떻게 동작하는지까지 쓴다(예: DI가 여러 구현체 중 하나를 고르는 규칙, Gradle Wrapper가 Gradle을 받아 오는 과정, Tomcat과 Spring의 역할 분리).
- 둘 이상을 비교하거나 다른 언어·프레임워크에 빗대면 헷갈리기 쉬운 쌍·세트를 표와 짧은 코드로 나란히 놓고(예: `init`과 constructor, `val`과 가변 컬렉션, `@Primary`·`@Qualifier`·`List<T>`), 함께 쓰일 수 있는 것끼리는 함께 쓰일 때 각자 맡는 역할도 쓴다(예: 레이어드·클린·헥사고날 아키텍처와 DDD).
- 같은 설명 문서를 데스크탑 전체판과 모바일 분할본으로 나누면, 사용자가 요약본을 요청하지 않은 한 두 판의 내용을 같게 두고 보기 방식만 다르게 하며, 입구 페이지나 목차에 두 판의 관계와 내용이 같다는 것을 적는다.

## 생긴 이유부터 푼다

구조·관례·규칙은 생긴 이유부터 푼다. 순서는 문제 배경 → 그 문제를 막으려고 생긴 규칙 → 그 규칙이 만든 불편 → 불편을 덜어 준 다음 규칙이다.

설명 중 새 개념이 나오면 그 자리에서 짧게라도 같은 순서로 푼다.

## 용어는 비유 → 정의 → 실제 예시 순으로

용어는 일상 비유나 친숙한 예시 → 정확한 정의 → 실제 맥락 예시 순서로 푼다. 비유·비교는 어디까지 맞고 어디서 어긋나는지 같이 쓴다.

새 용어에는 발음과, 정석 표현인지 대체 표현인지를 같이 적는다.
