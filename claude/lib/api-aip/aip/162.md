- 리소스의 revision 이력을 저장해도 된다(옛 판을 API로 노출할 가치가 있을 때, 다른 리소스가 서로 다른 revision에 기댈 때, 시간에 따른 변화를 표현해야 할 때).
- revision은 리소스 아래 중첩 컬렉션으로 추상화한다(권장); revision이 부모 리소스보다 오래 살아야 하면(리소스를 지운 뒤에도 남으면) 최상위 컬렉션이어도 된다.
- revision 메시지는 반드시 `google.api.resource`로 리소스 선언하고, 메시지 이름은 반드시 `{ResourceType}Revision`(`BookRevision`).
- 부모 리소스 메시지 타입의 `snapshot` 필드를 반드시 두고, 그 값은 반드시 revision을 만든 시점의 부모 설정이다; 생성 시각 `create_time`(`google.protobuf.Timestamp`)을 반드시 둔다; 그 revision이 함께 불리는 다른 ID 목록 `repeated string alternate_ids`(`latest` 등)를 둬도 된다.
- 생성 전략(부모가 바뀔 때마다·중요한 시스템 상태가 바뀔 때·명시적으로 요청할 때)은 무엇을 써도 되고, 어떤 전략인지 반드시 문서화한다.
- 특정 revision을 가리키는 하위 컬렉션 이름은 반드시 `revisions`; revision 이름은 `{resource_name}/revisions/{revision_id}` 꼴이다(`publishers/123/books/les-miserables/revisions/c7cfa2a8`).
- 서비스가 특정 ID를 별칭(`~/.claude/lib/api-aip/aip/122.md`)으로 예약해도 된다(`latest`; 읽기 전용이고 서비스가 관리); `latest`가 있으면 반드시 가장 최근에 만든 revision을 가리킨다(리소스의 현재 상태와 다를 수 있다).
- 사용자가 기존 revision에 별칭 ID를 붙이는 커스텀 메서드 `alias`를 둬도 된다; 요청엔 반드시 `name`(반드시 `REQUIRED`(`~/.claude/lib/api-aip/aip/203.md`), 반드시 `resource_reference`로 참조 리소스 타입 명시)과 `alias_id`(반드시 `REQUIRED`)를 둔다; 이미 쓰는 `alias_id`로 부르면 반드시 성공하고 그 별칭이 주어진 revision을 가리키게 바뀐다; 응답 타입은 규정이 없다(AIP 예시는 `Book`).
- 특정 revision으로 되돌리기는 `Rollback` 커스텀 메서드로 한다(권장): HTTP는 반드시 `POST`, 응답은 revision 리소스(권장); 요청엔 되돌아갈 설정을 지닌 revision을 가리키는 `name`을 반드시 두고, 반드시 `REQUIRED`, 반드시 `resource_reference`로 참조 리소스 타입을 밝힌다.
- revision 이력이 있는 리소스는 자식 리소스를 둬도 된다(리소스 전체의 자식이거나 revision 하나의 자식); revision을 가진 리소스를 여러 단계로 중첩하지 않는다(권장).
