- 같은 메이저 버전 안에서 소스 호환(기존 코드가 컴파일·실행), 와이어 호환(기존 클라이언트가 새 서버와 통신), 의미 호환(기존 코드가 기대한 동작)을 지킨다.
- 안전: 인터페이스·메서드·메시지·필드·enum·enum 값 추가(해도 된다). 단 새 필드의 기본 동작은 반드시 도입 전 동작과 같고, 서버가 채우던 필드는 중복이 생겨도 반드시 계속 채운다; 요청 전용 enum엔 값을 자유롭게 더해도 되고, 응답·리소스 enum에 값이 늘 수 있으면 문서화한다(권장).
- 깨지는 변경(반드시 하지 않는다, 표시한 곳은 권장):
  - 기존 요청 메시지·리소스에 필수 필드 추가
  - 컴포넌트 삭제, 이름 변경(=삭제+추가; 새 이름을 더하고 옛것을 남기는 건 된다)
  - 컴포넌트를 다른 파일로 이동(와이어는 호환이어도 C++·Python 등 생성 코드 파손), 기존 필드를 oneof 안팎으로 이동(Go 스텁 파손)
  - 필드·메시지 타입 변경(와이어 호환이어도), 기존 필드 값의 형식·생성 알고리즘 변경(OUTPUT_ONLY 포함)
  - 입력 `string` 필드의 크기 상한 증가(피한다, 권장)
  - 리소스 이름 변경; 유효한 이름 집합을 좁히기(기존 요청 실패)·넓히기(사용자 검증 로직 파손)(권장)
  - 정적 기본값 변경, 기본값 필드의 직렬화 방식 변경
  - 합리적인 사용자 코드를 깨뜨릴 동작·의미 변경
