```proto
enum BookView {  // proto 파일 최상위
  BOOK_VIEW_UNSPECIFIED = 0;  // 미지정: API가 정한 기본 view(예시는 BASIC)
  BOOK_VIEW_BASIC = 1;        // 기본 메타데이터만, 전체 내용 제외(ListBooks·GetBook 기본)
  BOOK_VIEW_FULL = 2;         // 전부
}
// 요청 메시지(GetBookRequest·ListBooksRequest 등)의 BookView view 필드로 받는다.
```
- 부분 응답은 필드 마스크 파라미터나 view enum 두 방식 중 하나로 지원해도 된다.
- 필드 마스크(`google.protobuf.FieldMask`)는 돌려줄 필드를 사용자가 세밀하게 고르게 한다; 마스크는 요청 메시지 밖 부가 채널(HTTP 쿼리 파라미터·HTTP 헤더·gRPC metadata, Google Cloud API는 system parameter)로 받고(권장) 요청 메시지 필드로 두지 않는다(권장).
- 파라미터 값은 반드시 `google.protobuf.FieldMask`이고 파라미터는 반드시 선택 사항이다; 명시적 `"*"`를 지원하고(권장) `"*"`면 반드시 모든 필드를 돌려준다; 생략하면 따로 문서화하지 않는 한 반드시 `"*"`로 본다; 이 기본값을 바꾸는 것은 깨는 변경이다(`~/.claude/lib/api-aip/aip/180.md`).
- update mask와 달리 중간(non-terminal) repeated 필드를 지나는 read mask를 허용해도 되지만 의무는 아니다.
- 노출할 조합이 적으면 view enum으로 부분 응답을 지원해도 된다: 요청 메시지의 `view` 필드로 받고(권장), enum 이름은 `View`로 끝내고(권장, `BookView`), 값은 최소 `BASIC`·`FULL`을 두고(권장) 다른 값을 더해도 된다.
- `UNSPECIFIED` 값은 반드시 유효(오류 아님)하고 그 동작을 반드시 문서화한다; 실제 기본값은 `List`면 `BASIC`(권장), `Get`·`Create`·`Update`·soft delete·커스텀 메서드면 `BASIC`이나 `FULL`(권장).
- enum은 `Get`·`List` 등 여러 요청에서 쓰이므로 proto 파일 최상위에 정의한다(권장, 최상위 enum이라 값에 enum 이름 접두어를 붙인다: `BOOK_VIEW_BASIC`); 값이 겹치지만 서로 다른 view가 여럿 필요하거나 필요해질 수 있으면 이름 충돌을 피해 view enum을 각 리소스 안에 중첩한다(권장).
- view에 필드를 시간이 지나며 더해도 되지만, view에서 필드를 빼는 것은 반드시 금지(깨는 변경).
- 표준 메서드의 기본 응답이 부분 응답이면 declarative 클라이언트가 덜 효과적이므로, 부분 응답이 꼭 필요하면 view처럼 전체 리소스를 요청할 수단을 둔다(권장).
- 요청 메시지의 단일 필드로 받는 read mask는 Google API에선 deprecated라 반드시 필드 마스크 파라미터(system parameter)를 쓴다; 기존 레거시 Google API와 Google 밖 API는 요청에 `google.protobuf.FieldMask read_mask` 필드 하나로 read mask를 받아도 된다.
- 그 필드는 반드시 `google.protobuf.FieldMask`이고 이름은 `read_mask`(권장), 선택 필드(권장); 명시적 `"*"`를 지원하고(권장) `"*"`면 반드시 모든 필드를 돌려준다; 마스크를 주지 않으면 반드시 모든 필드를 돌려준다; 중간 repeated 필드를 지나는 read mask를 허용해도 되지만 의무는 아니다.
