- 클라이언트는 다시 실행해도 의도치 않은 상태 변화가 없고, 트랜잭션이 아니며, 단항(unary) RPC인 요청을 자동 재시도한다(권장); 클라이언트 스트리밍·양방향 스트리밍은 이 규칙의 범위 밖이다.
- 트랜잭션 요청은 자동 재시도하지 않고(권장) 애플리케이션 수준 재시도 로직으로 트랜잭션 블록 전체를 처음부터 다시 실행한다(권장); 다시 실행하면 의도치 않은 상태 변화가 생기는 요청은 자동 재시도하지 않는다(권장).
- 위 조건을 갖춘 메서드면 `UNAVAILABLE`을 재시도한다(권장): 대개 네트워크 순간 장애로 생기는 일시적 오류라 연결이 곧 돌아온다고 보고 재시도한다.
- 아래 코드는 어떤 요청이든 자동 재시도하지 않는다(권장): `OK`(성공); `CANCELLED`(애플리케이션의 취소는 반드시 존중); `DEADLINE_EXCEEDED`(애플리케이션이 정한 기한은 반드시 존중); `INVALID_ARGUMENT`(다시 보내도 절대 성공하지 않는다); `DATA_LOSS`(복구 불가, 반드시 즉시 애플리케이션에 드러낸다).
- 아래 코드는 대체로 어떤 요청이든 자동 재시도하지 않는다(권장): `RESOURCE_EXHAUSTED`(쿼터 소진 신호면 몇 시간 동안 풀리지 않고 재시도가 과금을 부를 수 있다; 쿼터 밖의 이유로 쓰여 자원이 훨씬 빨리 풀리면 재시도 대상일 수 있다); `INTERNAL`(시스템 내부 일부가 고장 났다는 뜻으로 대개 버그를 제보할 일, 즉시 애플리케이션에 드러낸다(권장)); `UNKNOWN`(시스템도 모르는 오류라 재시도가 안전하지 않을 수 있다, 즉시 애플리케이션에 드러낸다(권장)); `ABORTED`(시퀀서 검사 실패·트랜잭션 중단, 개별 요청은 재시도하지 않고(권장) 트랜잭션 전체 같은 상위 수준에서 재시도한다(권장)).
- 컴포넌트 사이에 동기화·신호 없이 설계한 시스템이면 일부 코드를 자동 재시도해도 된다(예: 리소스가 생길 때까지 계속 기다리도록 설계한 읽기에서 `NOT_FOUND` 재시도); 다만 이런 설계는 대체로 권하지 않는다.
- 그래서 아래 코드는 어떤 요청이든 자동 재시도하지 않고(권장), 괄호 속 조건이 바뀌기 전엔 재시도하지 않는다(권장): `NOT_FOUND`(리소스가 생김), `ALREADY_EXISTS`(리소스가 지워짐), `PERMISSION_DENIED`(권한을 얻음), `UNAUTHORIZED`(인가됨), `UNAUTHENTICATED`(인증됨), `FAILED_PRECONDITION`(시스템 상태가 바뀜), `OUT_OF_RANGE`(범위가 넓어짐), `UNIMPLEMENTED`(RPC가 구현됨).
