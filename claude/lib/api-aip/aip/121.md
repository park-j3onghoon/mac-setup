- 설계 순서: 리소스(명사) → 리소스 간 관계·계층 → 리소스 스키마 → 메서드(동사); 커스텀 메서드보다 표준 메서드를 우선한다(권장).
- 리소스 계층으로 모델링한다(권장): 각 노드는 단일 리소스이거나 같은 타입 리소스의 컬렉션이다. API가 DB 스키마를 그대로 비춘다고 가정하지 않는다(권장).
- 요청·응답이 리소스이거나 리소스를 담으면 그 리소스 스키마는 모든 메서드(같은 서비스의 커스텀 메서드 포함)에서 반드시 같다.
- 모든 리소스는 반드시 Get을 지원한다(변경 뒤 상태 확인용); List도 반드시 지원한다(singleton은 예외: `~/.claude/lib/api-aip/aip/156.md`).
- 관리 평면(management plane) 작업이 끝나면(성공·오류, 장기 실행 작업(long-running operation, LRO)·동기 무관) 리소스 존재 여부와 사용자가 설정한 값은 반드시 안정 상태다: 마지막 변경이 create면 Get이 리소스를, update면 최종 값을, delete면 `NOT_FOUND`를 반드시 돌려준다.
- 프로토콜은 반드시 무상태: 요청 하나의 동작은 이전 요청과 독립이고, 리소스는 선행 요청 없이 바로 주소로 접근된다; 애플리케이션 상태는 클라이언트 몫이다.
- 리소스 참조와 부모·자식 관계는 반드시 방향 비순환 그래프(DAG)를 이룬다; output only 필드로 표현한 관계는 예외.
