```proto
message Config {
  option (google.api.resource) = {type: "api.googleapis.com/Config"
    pattern: "users/{user}/config" singular: "config" plural: "configs"};
  // name 등 필드
}
rpc GetConfig(GetConfigRequest) returns (Config) {
  option (google.api.http) = {get: "/v1/{name=users/*/config}"};
}
rpc UpdateConfig(UpdateConfigRequest) returns (Config) {
  option (google.api.http) = {patch: "/v1/{config.name=users/*/config}" body: "config"};
}
rpc ListConfigs(ListConfigsRequest) returns (ListConfigsResponse) {
  option (google.api.http) = {get: "/v1/{parent=users/*}/configs"};
}
message ListConfigsRequest {
  // users/- 는 모든 config, users/{user} 는 config 하나짜리 컬렉션(그땐 GetConfig를 쓴다)
  string parent = 1 [(google.api.resource_reference).child_type = "api.googleapis.com/Config"];
  // 나머지 표준 페이지네이션 필드
}
```
- singleton 리소스를 정의해도 된다; singleton은 반드시 부모가 있다는 것만으로 늘 존재하고, 부모마다 정확히 하나다.
- 사용자 지정 ID도 시스템 생성 ID도 반드시 두지 않는다; 리소스 이름(`~/.claude/lib/api-aip/aip/122.md`)은 부모 이름 뒤에 고정 세그먼트 하나를 붙인 꼴이고(`users/1234/config`) 늘 단수형이다(`users/1234/thing`).
- 리소스 정의엔 반드시 `singular`·`plural`을 둘 다 적는다; singleton이 다른 리소스의 부모가 돼도 된다.
- 표준 메서드 `Create`(`~/.claude/lib/api-aip/aip/133.md`)·`Delete`(`~/.claude/lib/api-aip/aip/135.md`)는 반드시 정의하지 않는다(부모를 만들거나 지울 때 암묵적으로 함께 생기고 사라진다); `Get`(`~/.claude/lib/api-aip/aip/131.md`)·`Update`(`~/.claude/lib/api-aip/aip/134.md`)를 정의하고(권장) 필요하면 커스텀 메서드를 둬도 된다; 모든 필드가 `OUTPUT_ONLY`(`~/.claude/lib/api-aip/aip/203.md`)면 `Update`를 반드시 정의하지 않는다.
- `List`(`~/.claude/lib/api-aip/aip/132.md`)를 정의해도 되지만 반드시 컬렉션 횡단 읽기 규칙(부모 ID 자리에 와일드카드 `-`를 받고, URI 패턴은 `-`를 박지 않고 `*` 유지, 지원 사실 문서화, 응답 이름엔 `-` 대신 실제 부모 ID)대로 구현한다; 보통 컬렉션을 나타내는 경로 끝 세그먼트는 singleton의 `plural`형으로 한다(권장, `/v1/{parent=users/*}/configs`); `-` 대신 실제 부모 ID를 주면 그 부모의 singleton 하나만 담은 컬렉션을 돌려준다(권장).
