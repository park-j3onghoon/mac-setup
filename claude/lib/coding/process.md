For frontend code, also Read `~/.claude/lib/coding/process-frontend.md`.

- Simplest structure first: where the repository has no convention for the structure, Read `~/.claude/lib/coding/architecture.md`, `~/.claude/lib/coding/domain.md`, `~/.claude/lib/coding/types.md` and `~/.claude/lib/coding/design.md` and build the simplest structure they describe; state scope/legacy/schedule compromises separately afterwards, and give the grounds whenever you call a design excessive or complex.
- Existing patterns first: before proposing or applying a change, a review agent's suggestion included, grep sibling modules for the pattern (`grep -r "{pattern}" {app}/`: an id field's default and lower bound, `VALID_TRANSITIONS` public/private, `Error` vs `Exception` naming) and follow it as Repository convention first in `~/.claude/lib/coding/index.md` says; when sibling modules differ, follow the form closest to the change (the same file, then the same module, then sibling modules) and, among equals, the most recent one; name the followed location in the result. When the question is where code belongs (a package, service or layer), count the cases the repository merged or deleted (history, PR bodies, documents) along with the ones it created, and ground the placement on the repository's history, documents and code rather than on a plan or an approval record.
- Verify before build: before adding field preservation, default mapping or error translation on the caller side, read the dependent system's write/merge/error behaviour in its proto, entity and repository (for example, whether an upsert replaces the whole record or merges fields).
- File state: before saying a file exists, changed or was deleted, check it with `git diff --name-only` / `ls` / `git status`, again after a branch switch or merge.
- Build after moves: after `git mv` or an import-path change, check the moved file's relative imports, prefer absolute imports, and run the project's build.
- Tracer bullet / vertical slice: deliver one thin end-to-end slice (entrypoint → use case → repository → storage → test) first and widen from there, one slice at a time.
- Two hats: put restructuring and approved behaviour/contract changes in separate commits. Preserve observable expectations during restructuring; test imports, organization and additional coverage may change without changing those expectations. Check equivalence as `~/.claude/lib/coding/tests.md` Refactoring equivalence says. When a feature is hard to add, first restructure under green until it is easy, then add the feature in its own commit.
- Final review: when the work is done, read the whole change once as its user (the flow they run, the screens and messages they see) and once for code quality, and make it shorter where it can be.
