# dev-plan 정량 일정 산정 레퍼런스

`/dev-plan`의 일정 산정 단계에서 적용하는 승수·산출 근거·출력 템플릿. SKILL 본문이 절차를 담고, 이 파일이 정량 기준을 담는다.

## 일정 산정 철학 (CRITICAL)

> **일정은 낙관적으로 잡지 않는다.** 변수와 리스크를 충분히 반영한 현실적 산정을 기본으로 한다.

모든 일정 산정에는 실제 발생 가능한 변수(미팅, 코드 리뷰, 긴급 대응 등)를 반영한다. 조기 완료 시 다음 작업을 앞당겨 진행한다.

## 1. 하루 가용 작업 시간 (요일별)

하루 8시간 중 고정 미팅과 변수를 제외한 실제 작업 가능 시간.

### 고정 미팅 (매주 반복)

| 요일 | 미팅 | 시간 | 빈도 |
|------|------|------|------|
| 매일 | 스크럼 | 30분 | 매일 |
| 월 | 주간 미팅 | 30분 | 매주 |
| 월 | 격주 미팅 | 1시간 | 2주 1회 |
| 화 | 격주 미팅 | 1시간 | 2주 1회 |
| 화 | 월간 미팅 | 1시간 | 월 1회 |
| 목 | 격주 미팅 | 1시간 | 2주 1회 |
| 금 | 주간 미팅 | 1시간 | 매주 |

격주/월간 미팅은 평균화하지 않는다. 매주 고정 미팅만 차감하고, 격주/월간이 겹치는 주(주당 1~2시간 추가)는 야근으로 흡수한다.

- **월**: 스크럼 30분 + 주간 30분 = **1h**
- **화**: 스크럼 30분 = **0.5h**
- **수**: 스크럼 30분 = **0.5h**
- **목**: 스크럼 30분 = **0.5h**
- **금**: 스크럼 30분 + 주간 1시간 = **1.5h**

### 변수 버퍼 (CRITICAL)

고정 미팅 외 예측 불가능한 업무(갑작스러운 코드 리뷰 요청, 긴급 버그 대응, 임시 미팅/논의, 컨텍스트 스위칭, 빌드/CI 대기·환경 이슈)로 **하루 1.5시간을 변수 버퍼로 차감한다.**

### 요일별 실제 작업 가능 시간

| 요일 | 총 시간 | 고정 미팅 | 변수 버퍼 | **작업 가능** |
|------|---------|-----------|-----------|--------------|
| 월 | 8h | 1h | 1.5h | **5.5h** |
| 화 | 8h | 0.5h | 1.5h | **6h** |
| 수 | 8h | 0.5h | 1.5h | **6h** |
| 목 | 8h | 0.5h | 1.5h | **6h** |
| 금 | 8h | 1.5h | 1.5h | **5h** |
| **주간 합계** | 40h | 4h | 7.5h | **28.5h** |

**주간 평균: 약 5.7h/일 (28.5h / 5일).** 격주/월간 미팅이 겹치는 주는 가용 시간이 1~2시간 줄지만 야근으로 흡수 가능하므로 산정에 반영하지 않는다.

## 2. AI 에이전트 기반 작업 시간 산정 (CRITICAL)

모든 작업은 **AI 코딩 에이전트(Claude Code 등)를 전면 활용**하는 것을 전제로 산정한다. 사람의 역할은 **지시(prompting) + 전체 코드 리뷰**이며, 직접 코딩 시간은 최소화한다.

### 작업 흐름

```
사람: 요구사항 정리 + 프롬프트 작성
  → AI 에이전트: 코드 생성
  → 사람: 생성된 코드 전체 리뷰 + 이해
  → (필요시) 사람: 피드백 → AI 에이전트: 수정
  → 사람: 최종 확인
```

### 작업 유형별 AI 시간 승수 (전통적 수동 코딩 대비)

승수는 **보수적으로 산정**한다. "예상보다 빨리 끝남" > "일정 밀림" 원칙. AI가 코드를 빠르게 생성해도 **사람이 전체 코드를 읽고 이해하는 시간**은 코드량에 비례하여 줄지 않으며, AI 오생성 디버깅/재지시(체감 20~30% 발생)도 포함해야 한다.

| 작업 유형 | 승수 | 시간 구성 비율 | 예시 |
|-----------|------|---------------|------|
| **고가속** (반복적, 패턴 기반) | **0.4~0.5x** | 지시 10% + AI 생성 대기 5% + 리뷰/이해 50% + 재지시/디버깅 15% + 최종 확인 20% | CRUD, 보일러플레이트, 설정, 마이그레이션, DTO |
| **중가속** (비즈니스 로직) | **0.6~0.7x** | 지시/설계 20% + AI 생성 대기 5% + 리뷰/이해 35% + 재지시/수정 25% + 최종 확인 15% | 서비스 로직, 유효성 검증, 도메인 규칙, API 연동 |
| **저가속** (복잡/창의적) | **0.8~0.9x** | 사람 설계 35% + AI 보조 10% + 리뷰 20% + 디버깅/수정 25% + 검증 10% | 아키텍처 결정, 복잡한 디버깅, 성능 최적화, 동시성 |

> **왜 보수적인가?**
> - 가장 엄밀한 연구(METR RCT, 2025): 숙련 개발자가 익숙한 코드베이스에서 AI 사용 시 오히려 19% 느려짐. 후속(2026)에서도 겨우 18% 빨라짐.
> - "50~80% 단축" 수치는 벤더 자체 보고 / 자기 평가 설문 기반이며, 실제 측정과 괴리가 큼.
> - 코드 전체를 이해하며 리뷰하는 워크플로우에서는 "AI가 빠르게 생성"한 이점이 상당 부분 상쇄됨.
> - 일정 철학: 낙관적으로 잡지 않는다. 변수를 반영한 현실적 산정.

### 단계별 시간 산정

각 PR의 일정을 아래 단계로 산정한다:

- **코드 구현 (지시 + AI 생성 + 리뷰)**:
  - "구현 시간" = 전통적 수동 코딩 시간 × 작업 유형별 승수
  - 프롬프트 작성, AI 출력 리뷰, 반복 수정, AI 재지시/디버깅이 모두 포함됨
  - **사람이 생성된 코드 전체를 읽고 이해하는 시간**이 포함됨 (가장 큰 비중)
  - AI 오생성 디버깅/재지시 시간 포함 (체감 20~30% 발생)
- **자체 QA (AI 테스트 생성 + 사람 검증)**:
  - 전통적 자체 QA 시간 × **0.5~0.6x**
  - AI가 테스트 코드를 생성하지만, 사람이 테스트 시나리오 적절성과 커버리지를 검증
- **코드 리뷰 대기 + 피드백 반영**:
  - 대기 시간: **0.5~1영업일** (리뷰어가 사람이므로 변동 없음)
  - 피드백 반영 1차: 전통적 반영 시간 × **0.4x** (AI가 구현하지만 사람이 확인)
  - 피드백 반영 추가 라운드: 1차의 **0.5x** (리뷰어 재요청, 발생 확률 ~30%)
  - → 기대값: 1차 반영 + (0.3 × 추가 라운드 대기 0.5일 + 추가 반영)
  - 대기 시간 중에는 **다음 PR 구현을 병렬 진행** (3. 파이프라인 참조)
- **QA**: QA 팀 검증 (해당 시, **0.5~1영업일**, 변동 없음)
  - QA 대기 중에도 **다음 PR 구현을 병렬 진행**

### 프론트엔드 작업: 두 가지 산정 (CRITICAL)

프론트엔드 작업은 **두 가지 일정을 병기**한다:

| 모드 | 구현 승수 | 자체 QA 승수 | 설명 |
|------|-----------|-------------|------|
| **꼼꼼 리뷰** | 위 표와 동일 | 위 표와 동일 | 코드 전체를 완벽히 이해 (백엔드와 동일 수준) |
| **빠른 리뷰** | 위 표의 **0.7x** | 위 표의 **0.7x** | 동작 확인 위주, 세부 로직 이해에 시간 덜 투자 |

예: 중가속 프론트엔드 작업의 전통적 구현 시간이 8h인 경우
- 꼼꼼 리뷰: 8h × 0.65 = 5.2h
- 빠른 리뷰: 8h × 0.65 × 0.7 = 3.6h

일정표에 `(꼼꼼/빠른)` 형태로 두 값을 병기한다.

### 산정 근거 및 한계

이 승수는 아래 연구/데이터를 참고하되, **보수적 방향으로 조정**함:
- METR RCT (2025, 가장 엄밀): 숙련 개발자 AI 사용 시 19% 느려짐 → 후속(2026) 18% 빨라짐
- 업계 자기보고 평균: 코딩 활동 33~36% 시간 단축 (대기업 보고, 자기 평가 포함)
- 작업 유형별 자기보고: 고반복 50~80% 단축, 비즈니스 로직 20~40%
- AI QA: 분석 6~10x 빨라짐 (OpenObserve), 테스트 시간 50% 단축 (ContextQA)
- **주의**: 자기보고와 실제 측정 사이에 큰 괴리가 있음 (METR). 벤더 보고는 최적 조건 기준.
- **이 승수는 초기값**이다. 실제 작업 경험이 쌓이면 프로젝트별로 보정할 것.

순수 작업 시간을 영업일로 환산할 때 **1. 요일별 가용 시간**을 적용한다.

## 3. 파이프라인 병렬화 및 캘린더 매핑 (CRITICAL)

PR을 독립적으로 설계했으므로, **리뷰/QA 대기 시간에 다음 PR 구현을 병렬 진행**한다.

### 파이프라인 구조

```
시간 →
PR-1: [구현+자체QA] → [리뷰 대기] → [피드백 반영] → [QA 대기] → 완료
PR-2:                  [구현+자체QA] → [리뷰 대기] → [피드백 반영] → ...
PR-3:                                  [구현+자체QA] → ...
                       ↑ PR-1 리뷰 대기 중 PR-2 착수
```

### 파이프라인 규칙

1. **PR-N을 리뷰에 제출하면 즉시 PR-N+1 구현 착수** (의존성이 없는 경우)
2. **PR-N이 PR-M에 의존하는 경우**: PR-M이 리뷰 제출된 후 PR-N 착수 가능 (머지 완료 대기 불필요, 인터페이스가 확정되었으므로)
3. **리뷰 피드백이 돌아오면**: 현재 진행 중인 작업을 중단점까지 마무리 → 피드백 반영 → 다시 진행 중이던 작업으로 복귀
4. **컨텍스트 스위칭 비용**: 작업을 전환할 때마다 **30분** 추가 (PR당 1~2회 발생)

### 캘린더 매핑

1. 시작일로부터 각 영업일의 가용 시간을 적용
2. 공휴일/휴가는 건너뜀
3. 코드 리뷰/QA 대기는 영업일 기준 (주말/공휴일에는 진행 안 됨)
4. **대기 시간은 다른 PR 구현으로 채움** → 전체 일정에서 대기 시간이 상당 부분 흡수됨
5. 단, 마지막 PR은 뒤에 채울 작업이 없으므로 대기 시간이 그대로 일정에 반영

```markdown

### 작업별 일정 (AI 에이전트 기반)

| PR | 유형 | FE/BE | 구현 (지시+생성+리뷰) | 자체QA | 리뷰+반영 | QA | 소계(영업일) |
|----|------|-------|---------------------|--------|-----------|-----|-------------|
| PR-1 | 고가속 | BE | 2.7h (6h×0.45) | 0.6h | 4.5h | - | 1.4일 |
| PR-2 | 중가속 | BE | 5.2h (8h×0.65) | 1h | 4.5h | - | 1.9일 |
| PR-3 | 중가속 | FE | 3.9h/2.7h (6h×0.65/×0.65×0.7) | 0.7h/0.5h | 4.5h | 4h | 2.5일/2.2일 |

### 캘린더 매핑 (파이프라인)

| 영업일 | 날짜 | 요일 | 가용시간 | 작업 내용 |

| 1 | 4/3 | 목 | 6h | PR-1 구현+자체QA → **리뷰 제출** |

| - | 4/5~6 | 토~일 | - | 주말 |
| 3 | 4/7 | 월 | 5.5h | PR-2 구현 계속 → PR-1 피드백 도착, 반영(1h) + 전환비용(0.5h) |
| 4 | 4/8 | 화 | 6h | PR-2 자체QA → **리뷰 제출**, PR-3 구현 시작 |
| ... | ... | ... | ... | ... |

> 리뷰/QA 대기 시간이 다음 PR 구현으로 채워져 **전체 일정이 단축**된다.
> 단, 피드백 반영을 위한 **컨텍스트 스위칭(PR당 0.5h)**이 추가된다.

### 요약

- **총 PR**: {N}개
- **순수 작업 시간**: {N}h (AI 에이전트 기반, 전통적 수동 코딩 대비 약 {N}% 수준)
- **영업일**: {N}일 ({시작일} ~ {종료일})
- **주 단위**: 약 {N}주
- **FE 빠른 리뷰 시**: {N}영업일 ({N}주) — FE 꼼꼼 리뷰 대비 {N}일 단축
- **병렬 가능 구간**: PR-1, PR-2 동시 진행 가능 → {N}영업일 단축
- **캘린더 이슈**: {공휴일/휴가 목록, 없으면 "없음"}
```

### 일정 산정 규칙 요약

- 1주 = 영업일 5일
- 영업일당 평균 작업 가능 시간: **5.35h** (요일별 차이 있음)
- 주간 작업 가능 시간: **26.75h**
- 공휴일/휴가 → 영업일에서 제외 (Google Calendar로 확인)
- 코드 리뷰 대기 → 영업일 기준 카운트
- 최종 일정은 **영업일 수**, **주 단위**, **시작일~종료일** 모두 표기
