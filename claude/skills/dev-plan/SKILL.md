# /dev-plan -- 개발 계획 및 작업 분할

개발 작업을 PR 단위로 분할하고, 의존성 기반 순서와 일정을 산정한다.

## 트리거 조건

- **명시적**: "개발계획 짜자", "작업 나누자", "일정 산정해줘" 등 직접 요청.
- **자동 (CRITICAL)**: 사용자가 작업 분할 없이 바로 개발에 착수하려 할 때(예: "이거 구현해줘"). 아래가 **모두** 해당되면 발동: ① 현재 세션에서 `/dev-plan` 미실행 ② 단일 파일 수정 수준을 넘는 규모 ③ 기존 작업 분할 계획 없음(Plan Mode 계획, 옵시디언 이슈 문서 등).
  - AskUserQuestion으로 확인: "작업이 여러 PR로 나뉠 수 있는 규모로 보입니다. 먼저 `/dev-plan`으로 작업을 분할하고 일정을 산정할까요? (Y/N)" → N이면 즉시 구현으로 진행.

## 사전 준비

- **Step 0 PRD**: AskUserQuestion으로 PRD(Product Requirements Document) 경로/URL 요청. 있으면 Read하여 요구사항 파악(`analysis.md` 있으면 함께 참고). 없으면 구두 설명받고 필요시 AskUserQuestion으로 구체화.
- **Step 1 Linear**: 관련 이슈 ID 요청. 있으면 `mcp__Linear__get_issue`로 description·하위 이슈·연결 이슈 조회. 없으면 분할 완료 후 생성 여부를 Step 7에서 처리.
- **Step 2 코드베이스**: 대상 레포 확인 → 관련 코드 구조·기존 패턴·아키텍처 확인 → 변경 필요한 레이어/모듈 식별.

## Step 3: 작업 분해

PRD/요구사항과 코드베이스 분석을 기반으로 작업을 분해한다.

### 분할 원칙

1. **PR 크기 목표 100~200줄** (diff 기준, 테스트 제외). 초과 예상 시 더 쪼갠다. 같은 레이어 작업을 너무 잘게 쪼개야 할 것 같으면 AskUserQuestion으로 합칠지 확인.
2. **아키텍처 원칙 기반 분할**: DDD(도메인 모델→리포지토리→서비스→컨트롤러), 클린(내부 Entity/UseCase→외부 Controller/Gateway), 레이어드(하위→상위), CQS(Command/Query 별도 PR). KISS/YAGNI(현재 필요한 것만, 미래 확장은 구조만 열고 코드는 안 씀). TDD(각 PR에 테스트 포함, 테스트 먼저).
3. **PR 단위 기준**: 하나의 PR은 하나의 논리적 변경. 리팩토링과 기능 추가를 섞지 않음. DB 마이그레이션·설정/인프라 변경은 별도 PR.
4. **PR 간 독립성 (CRITICAL)**: 각 PR이 독립적으로 구현·리뷰·QA 가능하도록 설계. PR-A를 리뷰/QA에 넘긴 동안 PR-B 구현 시작 가능해야 함. 의존성 있는 PR도 "머지 완료 후 시작"이 아니라 "리뷰 제출 후 다음 PR 착수 가능"한 구조로 분할(인터페이스/계약 먼저 정의 → 각 PR이 계약에 맞춰 독립 구현). 독립 분할이 어려우면 AskUserQuestion으로 "합칠지 / 인터페이스 분리 PR을 추가할지" 확인.

### 분할 출력 형식

각 PR마다: 제목, 설명(1~2줄), 변경 범위(파일 목록), 예상 diff(~N줄), 의존성(없으면 "없음"), 아키텍처 패턴, 테스트 종류(단위/통합/E2E), 작업 유형(고/중/저가속), 일정 산정(코드 구현(지시+생성+리뷰) / 자체 QA / 리뷰 대기+피드백 반영 / QA / 소계, FE는 빠른 리뷰 소계 병기).

## Step 4: 의존성 분석 및 순서 결정

1. **의존성 기반 정렬**: A가 B에 의존하면 B를 먼저 (Entity→Repository→Service→Controller; DB 마이그레이션→모델 변경→비즈니스 로직).
2. **의존성 없는 작업끼리**: 같은 도메인/기능끼리 묶어 배치, 의미가 비슷하면 규모가 작은 것부터.
3. **의존성 그래프**: Mermaid 다이어그램으로 표시.

출력 **실행 순서** 표: 순서 / PR / 제목 / 의존성 / 예상 시간.

## Step 5: 전체 일정 산정

**먼저 `ref-estimation.md`를 Read한다.** 이 단계의 모든 정량 기준(요일별 가용 시간, AI 승수표·산정 근거·출처, 파이프라인, 출력 템플릿)은 그 파일을 따른다.

`ref-estimation.md` 적용 절차:
1. **하루 가용 시간**(ref §1): 요일별 작업 가능 시간(월5.5/화6/수6/목6/금5h, 주 28.5h, 변수 버퍼 1.5h/일)을 순수 작업 시간 환산에 적용.
2. **캘린더 확인 (CRITICAL)**: Google Calendar MCP가 미인증이면 `mcp__claude_ai_Google_Calendar__authenticate`로 인증 후 작업 기간 이벤트 조회. 확인 사항 — 공휴일/회사 휴일, 연차/휴가, 고정 외 임시 미팅, 블로킹된 시간대. 공휴일/휴가는 영업일에서 제외, 추가 미팅 있는 날은 가용 시간 추가 차감. MCP 미사용 시 사용자에게 공휴일/휴가를 직접 받아 반영.
3. **AI 승수 적용 (CRITICAL)**: ref §2의 작업 유형별 승수(고 0.4~0.5x / 중 0.6~0.7x / 저 0.8~0.9x), 자체 QA(0.5~0.6x), 피드백 반영(1차 0.4x·추가 라운드 0.5x@30%), 리뷰/QA 대기(0.5~1영업일)를 단계별로 산정. FE는 꼼꼼/빠른(×0.7) 두 값 병기. 승수는 보수적(METR 등 출처는 ref).
4. **파이프라인 병렬화 (CRITICAL)**: ref §3 — 리뷰/QA 대기 중 다음 PR 병렬 진행, 컨텍스트 스위칭 PR당 30분.
5. **출력**: ref §4 전체 일정 출력 템플릿(작업별 일정 표 + 캘린더 매핑 + 요약).

## Step 6: 사용자 확인

전체 계획 출력 후 AskUserQuestion: "작업 분할과 일정이 적절한가요? 수정할 부분이 있으면 알려주세요." 수정 시 반영 후 다시 확인.

## Step 7: Linear 카드 생성

사용자 확인 완료 후, **반드시 사용자 확인을 받고** 진행:
- **기존 이슈 있음**: 각 PR을 하위 이슈로 생성할지 확인 → 승인 시 Linear GraphQL API로 생성(identifier 기반 parent 연결).
- **기존 이슈 없음**: 상위 이슈(제목=전체 작업명, 설명=PRD 링크+요약) + 각 PR 하위 이슈 생성할지 확인 → 승인 시 생성, 거부 시 스킵.
- **하위 이슈 포함 정보**: 제목 `PR-{N}: {제목}`, 설명(PR 설명+변경 범위+의존성+예상 시간), 마감일(일정 기반, 확인).

## Step 8: 옵시디언 저장

작업 계획을 옵시디언에 저장한다. **문서 내용·파일명·인덱스 템플릿은 `ref-estimation.md` §5를 따른다.**

## Step 9: 완료 메시지

```
개발 계획 완료:
- PR {N}개로 분할
- 예상 일정: {N}영업일 (약 {N}주) — {시작일} ~ {종료일}
- 캘린더 이슈: {공휴일/휴가 N일 제외} 또는 "없음"
- Linear: {이슈 URL 또는 "미생성"}
- 옵시디언: [[문서명]]

다음 단계: Plan Mode로 PR-1부터 상세 구현 계획을 수립하세요.
```

## Step 10: 자가 개선 (Self-improvement)

다음 단계(/plan-review)로 넘어가기 전에 학습 내용을 반영한다.

1. **일정 승수 보정**: 메모리에서 이전 dev-plan의 산정 vs 실제 소요를 비교, 오차 20%+면 해당 작업 유형 승수를 `ref-estimation.md`의 승수 표에 보정.
2. **분할 패턴**: 사용자가 합치거나 더 쪼갠 패턴을 분할 원칙에 반영.
3. **메모리**: 프로젝트 일정 맥락, 리뷰어 응답 속도 패턴 등.

업데이트할 내용이 있으면 1줄씩 나열 후 자동 반영. 없으면 스킵.

## 주의사항

- **이 스킬은 계획만 세운다. 코드를 작성하지 않는다.**
- Linear 이슈 생성은 **반드시 사용자 확인 후** 진행한다.
- 작업 규모가 PR 1개로 충분하면 분할하지 않고 바로 일정만 산정한다.
- 같은 레이어 작업을 쪼개야 하는지 애매하면 항상 사용자에게 물어본다.
- 일정 산정 시 "코드 구현 → 자체 QA → 코드 리뷰 → QA" 순서를 반드시 포함한다.
