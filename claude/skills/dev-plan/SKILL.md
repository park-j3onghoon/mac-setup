# /dev-plan -- 개발 계획 및 작업 분할

개발 작업을 PR 단위로 분할하고, 의존성 기반 순서와 일정을 산정한다.

## 트리거 조건

### 명시적 트리거
- "개발계획 짜자", "작업 나누자", "일정 산정해줘" 등 직접 요청

### 자동 트리거 (CRITICAL)
- 사용자가 **작업 분할 없이 바로 개발에 착수**하려 할 때 (예: "이거 구현해줘", "코딩 시작하자")
- 아래 조건이 **모두** 해당되면 자동 발동:
  1. 현재 세션에서 `/dev-plan`이 아직 실행되지 않았음
  2. 구현할 작업이 **단일 파일 수정 수준을 넘는** 규모 (예: 새 기능, 여러 파일 변경, 서비스 추가 등)
  3. 기존에 작업 분할이 완료된 계획이 없음 (Plan Mode 계획, 옵시디언 이슈 문서 등)
- 자동 트리거 시 AskUserQuestion으로 확인:
  > "작업이 여러 PR로 나뉠 수 있는 규모로 보입니다. 먼저 `/dev-plan`으로 작업을 분할하고 일정을 산정할까요? (Y: 작업 분할 진행 / N: 바로 구현)"
- 사용자가 N을 선택하면 즉시 구현으로 진행한다.

## 사전 준비

### Step 0: PRD 확인

AskUserQuestion으로 PRD(Product Requirements Document)를 요청한다:
> "관련 PRD 문서가 있나요? 있으면 경로나 URL을 알려주세요. (Confluence, 옵시디언, 로컬 파일 등)"

PRD가 있으면:
- 문서를 Read하여 요구사항을 파악한다
- 분석 문서(`analysis.md`)가 있으면 함께 참고한다

PRD가 없으면:
- 사용자에게 구현할 기능/변경사항을 구두로 설명받는다
- 필요시 AskUserQuestion으로 요구사항을 구체화한다

### Step 1: Linear 카드 확인

관련 Linear 이슈가 있는지 확인한다:

1. 사용자에게 질문:
   > "관련 Linear 이슈가 있나요? 있으면 이슈 ID를 알려주세요."

2. 이슈가 있으면:
   - `mcp__Linear__get_issue`로 상세 조회
   - description, 하위 이슈, 연결된 이슈 등 확인

3. 이슈가 없으면:
   - 작업 분할 완료 후 생성 여부를 물어본다 (Step 5에서 처리)

### Step 2: 코드베이스 파악

작업 대상 레포지토리와 관련 코드를 파악한다:
- 사용자에게 대상 레포 확인
- 관련 코드 구조, 기존 패턴, 아키텍처 확인
- 변경이 필요한 레이어/모듈 식별

## 작업 분할

### Step 3: 작업 분해

PRD/요구사항과 코드베이스 분석을 기반으로 작업을 분해한다.

#### 분할 원칙

1. **PR 크기 목표: 100~200줄** (diff 기준, 테스트 제외)
   - 200줄 초과 예상 시 더 쪼갠다
   - 같은 레이어의 작업을 너무 잘게 쪼개야 할 것 같으면 AskUserQuestion으로 확인:
     > "이 작업들은 같은 레이어(예: Repository 레이어)에 속해서 하나의 PR로 합치는 게 자연스러울 수 있습니다. 합칠까요, 분리할까요?"

2. **아키텍처 원칙 기반 분할**
   - **DDD (Domain-Driven Design)**: 도메인 모델 → 리포지토리 → 서비스 → 컨트롤러 순
   - **클린 아키텍처**: 내부 레이어(Entity, UseCase)부터 외부 레이어(Controller, Gateway)로
   - **레이어드 아키텍처**: 하위 레이어부터 상위 레이어로
   - **CQS (Command Query Separation)**: Command와 Query를 별도 PR로
   - **KISS / YAGNI**: 현재 필요한 것만 구현. 미래 확장은 구조만 열어두고 코드는 쓰지 않음
   - **TDD**: 각 PR에 테스트가 포함되어야 함. 테스트 먼저 작성

3. **PR 단위 기준**
   - 하나의 PR은 하나의 논리적 변경을 담는다
   - 리팩토링과 기능 추가를 같은 PR에 섞지 않는다
   - DB 마이그레이션은 별도 PR
   - 설정/인프라 변경은 별도 PR

4. **PR 간 독립성 확보 (CRITICAL)**
   - 각 PR은 가능한 한 **독립적으로 구현·리뷰·QA 가능**하도록 설계한다
   - PR-A를 리뷰/QA에 넘긴 동안 PR-B 구현을 시작할 수 있어야 한다
   - 의존성이 있는 PR도 "머지 완료 후 시작"이 아니라 "리뷰 제출 후 다음 PR 착수 가능"한 구조로 분할
   - 방법: 인터페이스/계약을 먼저 정의하고, 각 PR이 그 계약에 맞춰 독립 구현
   - 독립 분할이 어려운 경우 AskUserQuestion으로 확인:
     > "PR-{A}와 PR-{B}가 강하게 결합되어 독립 분할이 어렵습니다. 하나로 합칠까요, 인터페이스를 먼저 분리하는 PR을 추가할까요?"

#### 분할 출력 형식

각 작업(PR)에 대해 아래 정보를 정리한다:

```markdown
### PR-{N}: {PR 제목}

- **설명**: 이 PR에서 무엇을 하는지 1~2줄
- **변경 범위**: 수정/생성할 파일 목록 (예상)
- **예상 diff**: ~{N}줄
- **의존성**: PR-{M}에 의존 (없으면 "없음")
- **아키텍처 패턴**: 적용되는 패턴 (예: DDD Entity 정의, CQS Command 구현)
- **테스트**: 필요한 테스트 종류 (단위/통합/E2E)
- **작업 유형**: 고가속/중가속/저가속
- **일정 산정** (AI 에이전트 기반):
  - 코드 구현 (지시+생성+리뷰): {시간} (전통적 {시간} × {승수})
  - 자체 QA (AI 테스트+검증): {시간}
  - 코드 리뷰 대기 + 피드백 반영: {시간}
  - QA: {시간}
  - **소계**: {시간}
  - (프론트엔드인 경우) **빠른 리뷰 소계**: {시간}
```

### Step 4: 의존성 분석 및 순서 결정

#### 순서 결정 규칙

1. **의존성 기반 정렬**: A가 B에 의존하면 B를 먼저
   - 예: Entity → Repository → Service → Controller
   - 예: DB 마이그레이션 → 모델 변경 → 비즈니스 로직

2. **의존성이 없는 작업끼리**: 의미 단위로 그룹핑
   - 같은 도메인/기능의 작업끼리 묶어서 순서 배치
   - 의미도 비슷하다면 **작업 규모가 작은 것부터**

3. **의존성 그래프 시각화**: Mermaid 다이어그램으로 표시
   ```mermaid
   graph TD
     PR1[PR-1: Entity 정의] --> PR3[PR-3: Service 구현]
     PR2[PR-2: Repository 구현] --> PR3
     PR3 --> PR4[PR-4: Controller + API]
   ```

#### 출력: 실행 순서

```markdown
## 실행 순서

| 순서 | PR | 제목 | 의존성 | 예상 시간 |
|------|-----|------|--------|----------|
| 1 | PR-1 | Entity 정의 | 없음 | 2h |
| 2 | PR-2 | Repository 구현 | 없음 | 3h |
| 3 | PR-3 | Service 구현 | PR-1, PR-2 | 4h |
| 4 | PR-4 | Controller + API | PR-3 | 3h |
```

### Step 5: 전체 일정 산정

각 작업의 일정을 합산하여 **영업일 기준**으로 전체 일정을 산정한다.

#### 일정 산정 철학 (CRITICAL)

> **일정은 낙관적으로 잡지 않는다.** 변수와 리스크를 충분히 반영한 현실적 산정을 기본으로 한다.

이 원칙에 따라 모든 일정 산정에는 실제 발생 가능한 변수(미팅, 코드 리뷰, 긴급 대응 등)를 반영한다. 조기 완료 시 다음 작업을 앞당겨 진행한다.

#### 5-1. 하루 가용 작업 시간 계산

하루 8시간 중 **고정 미팅과 변수를 제외한** 실제 작업 가능 시간을 요일별로 계산한다.

##### 고정 미팅 (매주 반복)

| 요일 | 미팅 | 시간 | 빈도 |
|------|------|------|------|
| 매일 | 스크럼 | 30분 | 매일 |
| 월 | 주간 미팅 | 30분 | 매주 |
| 월 | 격주 미팅 | 1시간 | 2주 1회 |
| 화 | 격주 미팅 | 1시간 | 2주 1회 |
| 화 | 월간 미팅 | 1시간 | 월 1회 |
| 목 | 격주 미팅 | 1시간 | 2주 1회 |
| 금 | 주간 미팅 | 1시간 | 매주 |

##### 요일별 미팅 시간 (매주 고정분만 계산)

격주/월간 미팅은 평균화하지 않는다. 매주 고정 미팅만 차감하고, 격주/월간 미팅이 겹치는 주(주당 1~2시간 추가)는 야근으로 흡수한다.

- **월**: 스크럼 30분 + 주간 30분 = **1h**
- **화**: 스크럼 30분 = **0.5h**
- **수**: 스크럼 30분 = **0.5h**
- **목**: 스크럼 30분 = **0.5h**
- **금**: 스크럼 30분 + 주간 1시간 = **1.5h**

##### 변수 버퍼 (CRITICAL)

고정 미팅 외에도 예측 불가능한 업무가 발생한다:
- 갑작스러운 코드 리뷰 요청
- 긴급 버그 대응
- 임시 미팅/논의
- 컨텍스트 스위칭 비용
- 빌드/CI 대기, 환경 이슈 등

**하루 1.5시간을 변수 버퍼로 차감한다.**

##### 요일별 실제 작업 가능 시간

| 요일 | 총 시간 | 고정 미팅 | 변수 버퍼 | **작업 가능** |
|------|---------|-----------|-----------|--------------|
| 월 | 8h | 1h | 1.5h | **5.5h** |
| 화 | 8h | 0.5h | 1.5h | **6h** |
| 수 | 8h | 0.5h | 1.5h | **6h** |
| 목 | 8h | 0.5h | 1.5h | **6h** |
| 금 | 8h | 1.5h | 1.5h | **5h** |
| **주간 합계** | 40h | 4h | 7.5h | **28.5h** |

**주간 평균 작업 가능 시간: 약 5.7h/일 (28.5h / 5일)**

> 격주/월간 미팅이 겹치는 주에는 실제 가용 시간이 1~2시간 줄지만, 그 정도는 야근으로 흡수 가능하므로 일정 산정에는 반영하지 않는다.

#### 5-2. 캘린더 확인 (CRITICAL)

일정 산정 시 **반드시 Google Calendar MCP를 사용**하여 실제 캘린더를 확인한다.

1. Google Calendar MCP가 인증되지 않았으면 `mcp__claude_ai_Google_Calendar__authenticate`로 인증
2. 인증 완료 후, 작업 기간에 해당하는 날짜 범위의 이벤트를 조회
3. 확인 사항:
   - **공휴일**: 대한민국 공휴일, 회사 휴일 (캘린더에 등록된 것 기준)
   - **연차/휴가**: 사용자의 개인 일정
   - **추가 미팅**: 고정 미팅 외 임시 미팅이 잡혀 있는 날
   - **이미 블로킹된 시간대**: 다른 작업으로 예약된 시간
4. 캘린더에서 확인한 내용을 일정에 반영:
   - 공휴일/휴가일 → 영업일에서 제외
   - 추가 미팅이 있는 날 → 해당일 작업 가능 시간 추가 차감

Google Calendar MCP를 사용할 수 없는 경우:
- 사용자에게 알린다: "Google Calendar에 접근할 수 없습니다. 공휴일/휴가 일정을 직접 알려주세요."
- 사용자가 제공한 정보로 수동 반영

#### 5-3. AI 에이전트 기반 작업 시간 산정 (CRITICAL)

모든 작업은 **AI 코딩 에이전트(Claude Code 등)를 전면 활용**하는 것을 전제로 산정한다.
사람의 역할은 **지시(prompting) + 전체 코드 리뷰**이며, 직접 코딩하는 시간은 최소화한다.

##### 작업 흐름

```
사람: 요구사항 정리 + 프롬프트 작성
  → AI 에이전트: 코드 생성
  → 사람: 생성된 코드 전체 리뷰 + 이해
  → (필요시) 사람: 피드백 → AI 에이전트: 수정
  → 사람: 최종 확인
```

##### 작업 유형별 AI 시간 승수 (전통적 수동 코딩 대비)

승수는 **보수적으로 산정**한다. "예상보다 빨리 끝남" > "일정 밀림" 원칙.

AI가 코드를 빠르게 생성해도, **사람이 전체 코드를 읽고 이해하는 시간**은 코드량에 비례하여 줄지 않는다.
또한 AI가 잘못 생성하여 디버깅하거나 방향을 재지시하는 시간(체감 20~30% 발생)도 포함해야 한다.

| 작업 유형 | 승수 | 시간 구성 비율 | 예시 |
|-----------|------|---------------|------|
| **고가속** (반복적, 패턴 기반) | **0.4~0.5x** | 지시 10% + AI 생성 대기 5% + 리뷰/이해 50% + 재지시/디버깅 15% + 최종 확인 20% | CRUD, 보일러플레이트, 설정, 마이그레이션, DTO |
| **중가속** (비즈니스 로직) | **0.6~0.7x** | 지시/설계 20% + AI 생성 대기 5% + 리뷰/이해 35% + 재지시/수정 25% + 최종 확인 15% | 서비스 로직, 유효성 검증, 도메인 규칙, API 연동 |
| **저가속** (복잡/창의적) | **0.8~0.9x** | 사람 설계 35% + AI 보조 10% + 리뷰 20% + 디버깅/수정 25% + 검증 10% | 아키텍처 결정, 복잡한 디버깅, 성능 최적화, 동시성 |

> **왜 보수적인가?**
> - 가장 엄밀한 연구(METR RCT, 2025): 숙련 개발자가 익숙한 코드베이스에서 AI 사용 시 오히려 19% 느려짐. 후속(2026)에서도 겨우 18% 빨라짐.
> - "50~80% 단축" 수치는 벤더 자체 보고 / 자기 평가 설문 기반이며, 실제 측정과 괴리가 큼.
> - 코드 전체를 이해하며 리뷰하는 워크플로우에서는 "AI가 빠르게 생성"한 이점이 상당 부분 상쇄됨.
> - 일정 철학: 낙관적으로 잡지 않는다. 변수를 반영한 현실적 산정.

##### 단계별 시간 산정

각 PR의 일정을 아래 단계로 산정한다:

- **코드 구현 (지시 + AI 생성 + 리뷰)**:
  - "구현 시간" = 전통적 수동 코딩 시간 × 작업 유형별 승수
  - 이 시간에는 프롬프트 작성, AI 출력 리뷰, 반복 수정, AI 재지시/디버깅이 모두 포함됨
  - **사람이 생성된 코드 전체를 읽고 이해하는 시간**이 포함됨 (이 부분이 가장 큰 비중)
  - AI가 잘못 생성하여 디버깅/재지시하는 시간도 포함 (체감 20~30% 발생)
- **자체 QA (AI 테스트 생성 + 사람 검증)**:
  - 전통적 자체 QA 시간 × **0.5~0.6x**
  - AI가 테스트 코드를 생성하지만, 사람이 테스트 시나리오 적절성과 커버리지를 검증해야 함
- **코드 리뷰 대기 + 피드백 반영**:
  - 대기 시간: **0.5~1영업일** (리뷰어가 사람이므로 변동 없음)
  - 피드백 반영 1차: 전통적 반영 시간 × **0.4x** (AI가 구현하지만 사람이 확인)
  - 피드백 반영 추가 라운드: 1차의 **0.5x** (리뷰어가 재요청하는 경우, 발생 확률 ~30%)
  - → 기대값: 1차 반영 + (0.3 × 추가 라운드 대기 0.5일 + 추가 반영)
  - 대기 시간 중에는 **다음 PR 구현을 병렬 진행** (5-4 파이프라인 참조)
- **QA**: QA 팀 검증 (해당하는 경우, **0.5~1영업일**, 변동 없음)
  - QA 대기 중에도 **다음 PR 구현을 병렬 진행** (5-4 파이프라인 참조)

##### 프론트엔드 작업: 두 가지 산정 (CRITICAL)

프론트엔드 작업은 **두 가지 일정을 병기**한다:

| 모드 | 구현 승수 | 자체 QA 승수 | 설명 |
|------|-----------|-------------|------|
| **꼼꼼 리뷰** | 위 표와 동일 | 위 표와 동일 | 코드 전체를 완벽히 이해 (백엔드와 동일 수준) |
| **빠른 리뷰** | 위 표의 **0.7x** | 위 표의 **0.7x** | 동작 확인 위주, 세부 로직 이해에 시간 덜 투자 |

예: 중가속 프론트엔드 작업의 전통적 구현 시간이 8h인 경우
- 꼼꼼 리뷰: 8h × 0.65 = 5.2h
- 빠른 리뷰: 8h × 0.65 × 0.7 = 3.6h

일정표에 `(꼼꼼/빠른)` 형태로 두 값을 병기한다.

##### 산정 근거 및 한계

이 승수는 아래 연구/데이터를 참고하되, **보수적 방향으로 조정**함:
- METR RCT (2025, 가장 엄밀): 숙련 개발자 AI 사용 시 19% 느려짐 → 후속(2026) 18% 빨라짐
- 업계 자기보고 평균: 코딩 활동 33~36% 시간 단축 (대기업 보고, 자기 평가 포함)
- 작업 유형별 자기보고: 고반복 50~80% 단축, 비즈니스 로직 20~40%
- AI QA: 분석 6~10x 빨라짐 (OpenObserve), 테스트 시간 50% 단축 (ContextQA)
- **주의**: 자기보고와 실제 측정 사이에 큰 괴리가 있음 (METR). 벤더 보고는 최적 조건 기준.
- **이 승수는 초기값**이다. 실제 작업 경험이 쌓이면 프로젝트별로 보정할 것.

순수 작업 시간을 영업일로 환산할 때 **5-1의 요일별 가용 시간**을 적용한다.

#### 5-4. 파이프라인 병렬화 및 캘린더 매핑 (CRITICAL)

PR을 독립적으로 설계했으므로, **리뷰/QA 대기 시간에 다음 PR 구현을 병렬 진행**한다.

##### 파이프라인 구조

```
시간 →
PR-1: [구현+자체QA] → [리뷰 대기] → [피드백 반영] → [QA 대기] → 완료
PR-2:                  [구현+자체QA] → [리뷰 대기] → [피드백 반영] → ...
PR-3:                                  [구현+자체QA] → ...
                       ↑ PR-1 리뷰 대기 중 PR-2 착수
```

##### 파이프라인 규칙

1. **PR-N을 리뷰에 제출하면 즉시 PR-N+1 구현 착수** (의존성이 없는 경우)
2. **PR-N이 PR-M에 의존하는 경우**: PR-M이 리뷰 제출된 후 PR-N 착수 가능 (머지 완료 대기 불필요, 인터페이스가 확정되었으므로)
3. **리뷰 피드백이 돌아오면**: 현재 진행 중인 작업을 중단점까지 마무리 → 피드백 반영 → 다시 진행 중이던 작업으로 복귀
4. **컨텍스트 스위칭 비용**: 피드백 반영을 위해 작업을 전환할 때마다 **30분** 추가 (PR당 1~2회 발생)

##### 캘린더 매핑

파이프라인을 실제 날짜에 매핑한다:

1. 시작일로부터 각 영업일의 가용 시간을 적용
2. 공휴일/휴가는 건너뜀
3. 코드 리뷰/QA 대기는 영업일 기준 (주말/공휴일에는 진행 안 됨)
4. **대기 시간은 다른 PR 구현으로 채움** → 전체 일정에서 대기 시간이 상당 부분 흡수됨
5. 단, 마지막 PR은 뒤에 채울 작업이 없으므로 대기 시간이 그대로 일정에 반영

#### 5-5. 전체 일정 출력


2. **기존 Linear 이슈가 없는 경우**:

     b. 각 PR을 하위 이슈로 생성
   - 생성하지 않겠다고 하면 스킵

3. **Linear 이슈 생성 시 포함 정보**:
   - 제목: `PR-{N}: {PR 제목}`

## 주의사항

- **이 스킬은 계획만 세운다. 코드를 작성하지 않는다.**
- Linear 이슈 생성은 **반드시 사용자 확인 후** 진행한다.
- 작업 규모가 PR 1개로 충분한 경우, 분할하지 않고 바로 일정만 산정한다.
- 같은 레이어의 작업을 쪼개야 하는지 애매하면 항상 사용자에게 물어본다.
- 일정 산정 시 "코드 구현 → 자체 QA → 코드 리뷰 → QA" 순서를 반드시 포함한다.
