# /investigate — 체계적 디버깅

## Iron Law

**근본 원인 조사 없이 수정 금지.**
증상만 고치면 두더지 잡기 디버깅이 된다. 근본 원인을 찾고 나서 고쳐라.

## Phase 1: 근본 원인 조사

1. **증상 수집**: 에러 메시지, 스택 트레이스, 재현 단계. 맥락 부족하면 AskUserQuestion으로 **한 번에 하나씩** 물어라.

2. **코드 읽기**: 증상에서 역추적. Grep으로 모든 참조, Read로 로직 이해.

3. **최근 변경 확인**:
   ```bash
   git log --oneline -20 -- <affected-files>
   ```
   이전에 동작했는가? 뭐가 바뀌었는가? 회귀면 근본 원인은 diff에 있다.

4. **재현**: 버그를 결정적으로 트리거할 수 있는가? 못 하면 증거를 더 모아라.

**출력**: "근본 원인 가설: ..." — 무엇이 왜 잘못됐는지에 대한 구체적이고 검증 가능한 주장.

## Phase 2: 패턴 분석

| 패턴 | 시그니처 | 확인 위치 |
|---|---|---|
| Race condition | 간헐적, 타이밍 의존 | 공유 상태 동시 접근 |
| Nil/null 전파 | NoMethodError, TypeError | Optional 값 누락 가드 |
| 상태 오염 | 불일치 데이터 | 트랜잭션, 콜백, 훅 |
| 통합 장애 | 타임아웃, 예상 외 응답 | 외부 API, 서비스 경계 |
| 설정 드리프트 | 로컬 OK, 스테이징 실패 | 환경변수, 기능 플래그 |
| 캐시 오염 | 오래된 데이터 | Redis, CDN, 브라우저 캐시 |

git log에서 같은 영역의 과거 수정 확인 — **같은 파일에서 반복되는 버그는 아키텍처 문제의 신호.**

## Phase 3: 가설 검증

코드 수정을 쓰기 **전에** 가설을 검증:

1. **가설 확인**: 의심 지점에 임시 로그/assertion 추가. 재현 실행. 증거가 맞는가?
2. **가설이 틀리면**: Phase 1로 돌아가 증거를 더 모아라. 추측하지 마라.
3. **3-strike rule**: 가설 3개가 실패하면 **멈춰라**. AskUserQuestion:
   ```
   3개 가설을 테스트했으나 모두 불일치. 단순 버그가 아니라 아키텍처 이슈일 수 있음.
   A) 새 가설로 계속 조사: [설명]
   B) 사람 리뷰로 에스컬레이션
   C) 로깅 추가하고 다음 발생 시 잡기
   ```

**Red flags** — 보이면 속도를 줄여라:
- "일단 임시로 수정" — "일단"은 없다. 제대로 고치거나 에스컬레이션.
- 데이터 흐름 추적 전에 수정 제안 — 추측 중.
- 수정할 때마다 다른 곳에서 문제 발생 — 잘못된 레이어.

## Phase 4: 구현

근본 원인이 확인되면:

1. **근본 원인을 고쳐라, 증상이 아니라.** 실제 문제를 제거하는 최소 변경.
2. **최소 diff**: 가장 적은 파일, 가장 적은 줄.
3. **회귀 테스트 작성**:
   - 수정 **없이** 실패 (테스트가 의미 있음을 증명)
   - 수정 **있으면** 통과 (수정이 동작함을 증명)
4. **전체 테스트 스위트 실행**. 출력을 붙여넣어라. 회귀 불허.
5. **5개 이상 파일 수정 시**: AskUserQuestion으로 blast radius 경고.

## Phase 5: 검증 & 보고서

원래 버그 시나리오를 재현하여 수정 확인. **선택 사항 아님.**

```
DEBUG REPORT
════════════════════════════════════════
증상:          [사용자가 관찰한 것]
근본 원인:     [실제로 잘못된 것]
수정:          [무엇을 변경했는지, file:line 참조]
증거:          [테스트 출력, 재현 결과]
회귀 테스트:   [file:line]
관련:          [같은 영역의 과거 버그, 아키텍처 노트]
상태:          DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```

## 중요 규칙
- **3회 이상 수정 실패 → 멈추고 아키텍처를 의심하라.**
- **검증 못 하는 수정은 배포하지 마라.** 재현+확인 불가면 보내지 마라.
- **"이걸로 될 겁니다" 금지.** 검증하고 증명하라. 테스트를 돌려라.
- **5개 이상 파일 수정 → AskUserQuestion** blast radius 확인.
