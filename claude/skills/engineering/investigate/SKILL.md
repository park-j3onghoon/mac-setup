# /investigate: 근본 원인 디버깅

verify-before-fix: 증거로 확인된 근본 원인이 나온 뒤에 코드를 고친다. 증상만 고치면 두더지 잡기가 된다.

이미 난 문제의 원인을 좁히는 스킬이다. 작업 착수 전 배경·맥락을 모으는 것은 `/research`, 확정된 계획대로 만드는 것은 `/implement`.

1. 증상 수집: 에러 메시지·스택 트레이스·재현 단계를 모은다. 맥락이 비면 AskUserQuestion으로 한 번에 하나씩 묻는다. 서버에서 난 장애라 로그·메트릭이 필요하면 `~/.claude/lib/grafana/index.md`(있을 때)를 Read해 Loki·Prometheus를 조회한다. → 무엇이 언제 어떻게 실패하는지 한 문장으로 쓸 수 있다.
2. 역추적: 증상 지점에서 데이터 흐름을 거슬러 코드를 읽고 `git log --oneline -20 -- <affected-files>`로 최근 변경을 본다. 회귀면 근본 원인은 diff에 있다(구간이 넓으면 `git bisect`). 같은 파일에서 반복되는 버그는 아키텍처 문제의 신호(hotspot)다. → 의심 구간이 file:line 수준으로 좁혀졌다.
3. 결정적 재현: 버그를 원할 때 트리거하는 최소 절차나 테스트를 만든다. → 재현 루프가 red. 못 만들면 증거를 더 모아 2로 돌아간다.
4. 반증 가능한 가설: `근본 원인 가설: …` 로 무엇이 왜 잘못됐는지 구체적·검증 가능하게 쓴다. 안 잡히면 패턴과 대조한다: race condition · null 전파 · 상태 오염 · 통합 장애 · 설정 드리프트 · 캐시 오염. → 가설이 틀렸다면 어떤 관측이 나올지까지 적혀 있다.
5. 계측 검증: 의심 지점에 임시 로그·assertion을 넣고 재현을 돌려 가설을 반증해 본다. 빗나가면 2로 돌아간다. → 예측한 값이 실제 출력으로 확인됐다. 가설 3개가 연속으로 빗나가면 멈추고 AskUserQuestion으로 묻는다.
   ```
   3개 가설을 테스트했으나 모두 불일치. 단순 버그가 아니라 아키텍처 이슈일 수 있음.
   A) 새 가설로 계속 조사: [설명]
   B) 사람 리뷰로 에스컬레이션
   C) 로깅 추가하고 다음 발생 시 잡기
   ```
6. 최소 diff 수정: 근본 원인만 고친다. "일단 임시로" 요청이 와도 선택지는 근본 수정 아니면 에스컬레이션이다. 회귀 테스트는 수정 없이 red · 수정 있으면 green 을 둘 다 눈으로 확인하고, 관련 테스트를 돌려 출력을 증거로 붙인다(전체 스위트가 로컬에서 안 도는 레포는 CI가 게이트). 5개 이상 파일을 건드리면 AskUserQuestion으로 blast radius를 확인받는다. → 재현 루프가 green, 관련 테스트 회귀 0.
7. 보고: 원래 버그 시나리오를 재현해 수정을 확인한다(확인 불가면 BLOCKED, hotspot·잔여 우려가 있으면 DONE_WITH_CONCERNS). → 아래 형식으로 출력했다.

```
DEBUG REPORT
════════════════════════════════════════
증상:          [사용자가 관찰한 것]
근본 원인:     [실제로 잘못된 것]
수정:          [무엇을 변경했는지, file:line]
증거:          [테스트 출력, 재현 결과]
회귀 테스트:   [file:line]
관련:          [같은 영역의 과거 버그, 아키텍처 노트]
상태:          DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```

보고서까지가 이 스킬의 범위다. 고치기로 했으면 `/implement`, 고친 뒤 push 전 점검은 `/review`다.

원인 구조가 복잡해 그림이 있어야 전달되면 `~/.claude/lib/explain-html.md`를 Read해 같은 내용을 HTML 해설서로 낸다.
